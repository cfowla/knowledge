# Reusable Evaluation Controls — arXiv:2608.18066v1

Source: **On the Fragility of Self-Improving Agents: Variance, Task Order, and Underspecification** (arXiv:2608.18066v1, 2026-08-18)

## Controls to reuse

- **Repeat whole-sequence runs.** Report mean task success plus cross-run standard deviation and the best–worst run gap. The paper used three runs; treat that as the study design, not a universal minimum.
- **Randomize task order.** Evaluate the published/default sequence and multiple shuffled sequences. A stateful self-improvement system can be benefiting from a hidden curriculum rather than from a robust learning mechanism.
- **Audit task-order difficulty.** Plot task success or difficulty across sequence position to detect easy-to-hard, clustered, or oscillating curricula before interpreting self-improvement gains.
- **Use a strong no-memory baseline.** Re-run older self-improvement methods on a contemporary base model and harness so gains are not artifacts of weak initialization.
- **Separate agent noise from learning-loop noise.** Quantify baseline run variance before layering stateful memory or self-improvement on top.
- **Control reward/evaluator noise during diagnosis.** When isolating memory dynamics, use the cleanest available evaluation signal; this paper supplied ground-truth reward instead of an LLM judge to avoid an extra noise source.
- **Expose rubric specificity to the memory builder when appropriate.** Detailed evaluator criteria can disambiguate intended task outcomes, but keep this information confined to the post-task learning step if the test is intended to measure the original agent policy unchanged.
- **Feed environment execution errors into memory construction.** Failed clicks, stale element references, unsupported actions, and other interaction feedback should be available to the learning component so it does not encode an invalid trajectory as reusable advice.
- **State environment constraints explicitly.** The memory prompt should distinguish executable from non-executable strategies and discourage unsupported API calls, external sites, or human-confirmation loops when those actions are unavailable.
- **Audit memory for contamination.** Track unsupported strategies, repeated keywords, and when a questionable memory first appears; early stochastic errors can propagate and become increasingly retrieved.
- **Inspect evaluator bugs as learning hazards.** A false negative is not merely a scoring problem when reward or reflection feeds back into memory; it can create a wrong lesson that affects later tasks.
- **Stress-test underspecified tasks separately.** Pilot on well-specified tasks, then test ambiguous or underspecified tasks as a worst-case reliability condition rather than averaging them into one headline score.
- **Require a memory-validation boundary.** Treat stored memories as hypotheses until checked for task relevance, environment compatibility, and evaluator correctness.
- **Preserve human intervention paths.** For irreversible or long-running systems, provide operators a way to inspect, reject, or correct learned memories before they cascade.

## Minimal protocol template

1. Lock model, harness, benchmark version, and evaluation functions.
2. Run the no-memory baseline repeatedly and quantify run variance.
3. Run each self-improvement method under the default order with the same repetitions.
4. Re-run under at least two independently shuffled task orders.
5. Compare mean performance, standard deviation, and best–worst gaps.
6. Plot task difficulty/success versus sequence position to detect implicit curricula.
7. Audit memory items for unsupported actions, task misinterpretation, evaluator-induced lessons, and recurring contaminants.
8. Add rubric detail, environment feedback, and explicit constraint prompts one at a time, then jointly.
9. Confirm improvements persist across task orders and do not merely restore the default-order curriculum.
10. Before deployment, test deliberately underspecified cases and define memory validation plus human override.

## Boundary

These controls are extracted from a web-agent benchmark study. They are directly reusable as evaluation design patterns, but the paper does not establish that the same effect sizes or the exact three-run design generalize to other agent domains.
