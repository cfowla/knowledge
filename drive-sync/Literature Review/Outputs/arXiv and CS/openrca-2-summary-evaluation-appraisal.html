One-page synthesis

Core thesis: outcome-only RCA benchmarks let LLM agents appear successful when they name the correct root-cause service but fail to produce a verified causal path from fault to symptom. OpenRCA 2.0 tries to close this gap by supervising the diagnostic process itself: root-cause labels plus step-wise causal propagation graphs.

The paper introduces PAVE—Path Annotation via Verified Effects—a pipeline that uses information available to the benchmark builder but hidden from the RCA agent: the known fault-injection intervention. Instead of asking annotators or algorithms to infer backward from symptoms, PAVE performs forward verification from the injected cause, admitting a causal path only when it satisfies structural plausibility, statistical deviation from a baseline, and upstream-to-downstream temporal alignment.

Applying PAVE yields OpenRCA 2.0, a 500-instance benchmark spanning TrainTicket, OpenTelemetry Demo, and DeathStarBench Hotel Reservation. The reported model results show a large gap between service localization and causal grounding: across 11 models, exact root-cause-set recovery averages 20.7%, any correct service is named in 76.0% of cases, but path reachability is only 61.5%. This makes the paper valuable for agent-harness design because it operationalizes a core evaluation principle: score the derivation, not only the final answer.

Section-by-section condensation

Abstract

The abstract frames RCA as a demanding LLM-agent task requiring long-context telemetry interpretation, multi-step reasoning, and tool use. Existing datasets usually label only the originating component, which can reduce evaluation to a final-answer classification task and mask whether the agent’s explanation is causally grounded.

PAVE reconstructs causal propagation paths from known fault injections via forward verification. OpenRCA 2.0 contains 500 step-wise annotated instances; across 11 frontier models, exact root-cause-set recovery averages 20.7%, while agents identify at least one correct service in 76.0% of cases but ground it in a verified path in only 61.5%.

1. Introduction

The introduction argues that microservice failures propagate through networked service graphs, so the initial fault may be remote from the first observed symptom. Prior benchmarks built from fault injection usually treat the injected component as the ground-truth label and score whether the agent names it, leaving the causal derivation unexamined.

The authors define ungrounded diagnosis as the case where an agent identifies a correct root-cause service but lacks a verified propagation path to the observed failure. The key insight is information asymmetry: benchmark builders know the intervention that started the cascade, so they can verify forward from cause to effects rather than perform the same backward abductive inference required of the agent.

2. PAVE: Path Annotation via Verified Effects

PAVE models the microservice system as a directed dependency graph over services, pods, and hosts. It consumes the dependency graph, raw telemetry across the injection window, and the recorded intervention, then emits a verified path set. Phase 1 performs structural pruning: telemetry is abstracted into node-type-aware states and candidate paths are generated using propagation rules and constrained DFS over a time-expanded graph.

Phase 2 performs causal verification: each candidate path is checked against a pre-injection reference baseline using distributional tests suited to the metric type. A path is admitted only if every node deviates from baseline, every edge conforms to a known propagation rule, and downstream anomaly onset is temporally consistent with upstream causation. This design favors precision over recall by dropping cases or paths that fail the full joint screen.

3. Experiments

The experimental setup uses three distinct microservice systems: TrainTicket, OpenTelemetry Demo, and Hotel Reservation. Fault-injection workloads cover 27 chaos primary kinds across application, resource, network, and pod-level faults. From 8,137 injected runs, the authors filter silent injections, apply PAVE, and curate 500 evaluable instances using stratified selection across system, chaos family, and root service.

All evaluated agents share the same ReAct-style tool-augmented architecture, telemetry tools, prompt templates, and structured answer schema. Outcome metrics grade the predicted root-cause set; process metrics grade causal-path quality using Path Reachability, Node F1, Edge F1, and SQL evidence executability. The result is a comparison of model backbones under a fixed investigative harness rather than an uncontrolled comparison of agent frameworks.

3.2 Benchmark utility

The headline result is that service localization substantially overstates diagnostic quality. Average AnySvc is 76.0%, but mean PR is 61.5%; strict exact match is 20.7% and pair-level F1 is 34.1%. This exposes cases where an agent names a correct service but does not connect it to the symptom through a verified propagation path.

Process-level graph structure is harder than affected-node identification: mean Edge F1 is 43.4%, while mean Node F1 is 62.2%, a gap of 18.8 percentage points. The top result varies by metric, so the paper argues there is no single dominant model backbone; model choice depends on whether the operational priority is recall, precision, path validity, or evidence executability.

3.3 Failure mode characterization

The authors manually inspect trajectories to identify three recurring failure modes: premature commitment under under-exploration, presence bias toward observable activity, and salience capture by the loudest signal. These map well to real agentic failure modes: stopping early after a plausible root cause, treating missing telemetry as absence of fault, and over-weighting high-volume downstream symptoms.

The case study shows Claude naming the correct root-cause service but hallucinating a direct edge that skips intermediate services in the ground-truth path. Outcome-only scoring would count the correct service as a success; process-level scoring exposes the missing causal structure that an on-call engineer would still need.

3.4 Annotation reliability

A two-annotator audit of 100 uniformly sampled instances reports 94% case-level agreement on the validity of the PAVE-produced causal graph. The annotators were paper authors with distributed-system observability expertise, and they judged whether each edge was plausibly causal and whether obvious propagation edges were missing.

All six disagreements were one-directional: at least one annotator thought an additional path was plausible, but no included edge was judged implausible. This supports the paper’s precision-favoring claim, but the audit is not independent in the strongest sense because annotators were authors and the sample size is limited.

4. Related work

The related-work section positions the paper against earlier RCA benchmarks and approaches that treat fault localization as classification or ranking. LLM-based RCA shifts the task toward generative causal explanation, but the benchmark labels have largely remained outcome-only, creating a mismatch between the reasoning ability being claimed and the supervision being used.

The authors connect PAVE to causal discovery and process supervision. Unlike observational causal discovery, PAVE uses interventional information from controlled fault injection to transform inference into verification. Unlike process-supervision work in math or code, systems diagnosis lacks a natural proof checker or compiler, so PAVE supplies a domain-specific verification substrate.

5. Assumptions and threats to validity

The authors state four core input assumptions: a true controlled intervention, a sufficiently complete dependency graph, observable propagation signatures in traces/metrics/logs, and a clean enough pre-injection baseline. If these fail, the benchmark scores should be treated as upper bounds rather than transferable estimates.

Internal threats include an incomplete propagation rule vocabulary and permissive per-node anomaly screens. The authors argue that the conjunctive end-to-end gate controls false positives, but external validity remains bounded by controlled synthetic testbeds. Production-scale, service-mesh, serverless, and fully event-driven environments would require recalibration rather than direct score transfer.

6. Conclusion

The conclusion restates the paper’s main contribution: PAVE turns known fault injections into verified causal-process labels, and OpenRCA 2.0 uses those labels to evaluate whether RCA agents can ground a diagnosis in a path rather than merely name a service.

The practical implication is broader than RCA: diagnostic agents need evaluation methods that separate correct localization from correct reasoning. Step-wise causal ground truth raises the trust bar from “right answer” to “right answer for the right, evidence-supported path.”

Appendices A–H

The appendices provide dataset documentation, testbed topology, root-cause taxonomy, PAVE pipeline details, audit protocol, agent architecture, prompt and schema design, metric definitions, and auxiliary tables. The dataset contains multimodal pre- and post-injection telemetry in parquet format, structured ground-truth labels, and causal graphs; intended uses include process-level evaluation and future process-reward-model training.

The most implementation-useful appendix material is the schema and harness design: strict ground-truth causal graphs, strict agent JSON, mandatory executable SQL evidence for every root-cause and propagation-edge claim, investigation/synthesis prompt separation, and deterministic metric definitions. These are directly reusable ideas for broader agent evaluation harnesses.

Benchmark and evaluation design extraction

PAVE pipeline

INPUTS:
  G: dependency graph over services, pods, hosts, spans
  O(t): raw telemetry over normal and abnormal windows
  do(vroot): recorded intervention with target, fault type, window, parameters

PHASE 1 — STRUCTURAL PRUNING:
  1. Project raw telemetry to discrete states using node-type-aware abstraction Ψ.
  2. Use propagation rules R to admit only mechanism-plausible transitions.
  3. Run constrained DFS over a time-expanded heterogeneous graph.
  4. Output Πcand, a candidate path set.

PHASE 2 — CAUSAL VERIFICATION:
  1. Establish a pre-injection reference baseline.
  2. Apply metric-specific deviation tests:
       - Z-score detector for approximately Gaussian CPU/memory metrics
       - Percentile detector for heavy-tailed counts/errors
       - Adaptive latency detector for request-latency metrics
  3. Accept a path only if:
       - every node is anomalous vs baseline
       - every edge conforms to R
       - downstream onset follows upstream onset
  4. Output Π*, the verified path set.

DESIGN BIAS:
  High precision, lower recall.
  Borderline weakly supported paths are intentionally excluded.

Agent architecture

CONTROL FLOW:
  START
    → llm_call
    → if tool_calls: tool_node → llm_call → ...
    → compress_rca_findings
    → END

TOOLS:
  list_tables_in_directory
    - discover parquet files and metadata
  get_schema
    - inspect columns, types, row counts
  query_parquet_files
    - execute SQL over parquet files
  think_tool
    - record interim reasoning and next investigative step

BUDGET:
  - recommended ~50 tool calls
  - hard cap 100 tool calls
  - all models share tool definitions and retry logic

IMPORTANT DESIGN CHOICE:
  Investigation prompt withholds final JSON schema.
  Synthesis prompt converts accumulated evidence into strict JSON.
  This separates evidence collection from answer packaging.

Metric stack

  EM:

  Precision / Recall / F1:

  AnySvc:
    at least one predicted root-cause service is correct, ignoring fault kind

PROCESS METRICS:
  Path Reachability (PR):

  SQL Exec:

Main strengths

  • Clear evaluation target: separates root-cause localization from causal-path grounding.
  • Process labels: provides node/edge causal graphs rather than only outcome labels.
  • Controlled annotation advantage: exploits known interventions to verify forward instead of asking annotators to infer backward.
  • Deterministic scoring: schema-based graph metrics and SQL executability reduce reliance on subjective LLM-as-judge evaluation.
  • Tool-use realism: agents query traces, logs, and metrics through tools rather than answering from a static text prompt.
  • Failure-mode clarity: premature commitment, presence bias, and salience capture are actionable design targets.

Main limitations

  • Synthetic/testbed envelope: the benchmark covers controlled systems and injected faults, not production incident diversity.
  • Precision-favoring ground truth: false positives may be low, but weak real paths may be excluded, affecting recall-sensitive evaluation.
  • Rule-set dependence: propagation mechanisms outside the authored rule vocabulary may be silently pruned.
  • Author-only audit: manual reliability is useful but not equivalent to independent external annotation.
  • No train/dev/test split: the dataset is positioned for evaluation; training on it risks leakage unless future splits or governance are added.
  • Model-era volatility: frontier-model rankings are less durable than the benchmark design pattern.

Bottom-line appraisal

Best use: Use this paper as a design reference for agent benchmarks that need to score reasoning paths, not only final outputs. The most reusable parts are PAVE’s forward-verification logic, the ground-truth/agent schema separation, mandatory executable evidence, and the outcome/process metric split.
Do not use for: Production certification of RCA agents, broad claims about all cloud systems, or durable ranking of model vendors. The paper is stronger as a harness architecture and benchmark-methods contribution than as proof that any specific model is operationally reliable.

Implementation and practice takeaways

Build pattern
Score reasoning artifacts, not just answers

For any diagnostic agent, require a structured path: hypothesis, evidence, intermediate states, causal edges, and final conclusion.

Schema pattern
Separate ground truth from answer contract

Ground truth can be rich; agent output should be strict, smaller, and mechanically scoreable.

Evidence pattern
Require executable evidence

Every root cause and edge should carry a re-runnable query, citation, log reference, or deterministic evidence pointer.

Prompt pattern
Separate investigation from synthesis

Let the agent collect evidence before forcing JSON. Then synthesize into a strict contract.

Metric pattern
Use paired outcome/process metrics

Track final-answer accuracy separately from graph/path/evidence fidelity.

Safety pattern
Detect “correct answer, wrong reason”

In safety-sensitive workflows, an answer without a valid path should not receive full credit.

  allowed_output_schema/

  1. Investigate with tools.
  2. Record intermediate evidence.
  3. Emit strict structured output.
  4. Attach evidence to every claim and edge.

JUDGE:
  1. Validate schema.
  2. Re-run or resolve evidence pointers.
  3. Score final answer.
  4. Score process graph/path.
  5. Score evidence support.
  6. Report failure taxonomy.

REPORT:
  - correct final answer + valid process
  - correct final answer + invalid process
  - incorrect final answer + partial process
  - unsupported claims
  - missing evidence
  - invalid evidence execution

Direct next steps for a builder

  1. Adopt a two-layer metric model: outcome and process.
  2. Define a minimal causal graph schema for your task domain before collecting cases.
  3. Require evidence objects to be machine-checkable wherever possible.
  4. Track ungrounded success explicitly: correct final answer but failed path/evidence.
  5. Build a failure taxonomy aligned with intervention targets: premature commitment, missing negative evidence, salience bias, hallucinated edge, unsupported claim.
  6. Use a small independently audited calibration set before trusting automated labels.
