One-page synthesis

Core thesis: the configuration-and-process layer around LLM coding agents should be treated as governed software infrastructure. The paper argues that agent rules, permission declarations, prompts, trace records, and workflow gates need deterministic controls because the harness/model pair should not be trusted to govern itself.

The paper identifies a “thin governance surface” in modern coding harnesses: IDE-integrated agents can read, write, execute shell commands, use MCP tools, and act across a codebase, but the files that steer them are usually natural-language markdown or YAML artifacts with weak provenance, weak permission enforcement, little cross-tool portability, and no guaranteed requirement-to-test trace. Rel(AI)Build is presented as a deterministic control plane above the harness, not as a replacement for Cursor, Claude Code, Copilot, Codex, Windsurf, OpenCode, or Kiro.

The strongest empirical contribution is the prevalence study: 10,008 public GitHub repositories and 6,145 agent config files show substantial exact duplicate propagation, shallow version-control depth, and very sparse declared permission boundaries. The strongest architecture contribution is the mapping from each observed governance gap to a simple deterministic mechanism: SHA-256 addressing, HMAC-stamped lockfiles, hash-chained audit logs, tiered permissions, attack-derived command/path blocklists, a phase state machine, trace artifacts, a canonical-to-target compiler, and Jaccard drift triage.

Bottom line: read as a build-oriented control-plane pattern, not as proof that Rel(AI)Build improves engineering productivity or security in the field. The architecture is valuable because it separates deterministic governance from probabilistic LLM behavior; the evidence remains early-stage.

Section condensation

Abstract

The abstract frames the central risk: coding harnesses give agents broad file and shell access, but their steering layer—rules files, agent definitions, and IDE-specific markdown—is generally unmanaged. The prevalence study’s most robust finding is exact duplicate propagation of agent configurations across independent repositories, suggesting that prompts and agent rules circulate like undeclared shared components.

The proposed remedy is a deterministic control plane called Rel(AI)Build. It content-addresses agent definitions, stamps lockfiles, writes hash-chained logs, enforces tiered permissions and attack-derived blocklists before LLM invocation, gates feature work through a phase machine, compiles canonical definitions to seven targets, and uses Jaccard similarity to detect prompt drift. The abstract explicitly limits its claim: conformance tests show mechanisms enforce stated invariants, while developer outcomes remain future work.

1. Introduction

The introduction describes agent configuration as a high-authority but low-governance artifact. Agent rules may encode architectural conventions, dependency preferences, tool permissions, and process expectations, yet they are often copied, edited casually, trusted without provenance, and injected into context for tools that can write files or execute commands. The paper separates three recurring gaps: unmanaged configuration, unbounded execution, and non-portable expertise across harness dialects.

The thesis is deliberately narrow: RBAC, sandboxing, orchestration, stage gates, and supply-chain controls are not new. The claimed contribution is applying deterministic, tool-agnostic governance to the layer surrounding coding agents. The contribution list is useful because it distinguishes architectural mechanisms from empirical activities and states a determinism boundary: install-time gates and state transitions are deterministic; trace linkage still depends on cooperative agent behavior.

2. Background and related work

The background positions Rel(AI)Build beside, not inside, coding harnesses and orchestration frameworks. Cursor, Claude Code, Copilot, Aider, Codex, Windsurf, and related tools differ in configuration files, context scoping, native augmentation, and runtime enforcement, but share a thin configuration interface. Multi-agent frameworks such as LangGraph, CrewAI, AutoGen, SWE-Agent, and OpenHands focus on orchestration or autonomous issue resolution, whereas this paper focuses on governance of prompts, permissions, and process artifacts that steer existing IDE-integrated harnesses.

The paper grounds its design in several established traditions: least privilege and capability-based security, policy-as-code, infrastructure-as-code, supply-chain security, SBOM framing, SLSA-style integrity, stage-gate workflow governance, formal workflow verification, and tamper-evident logging. This related-work section is methodologically useful because it avoids claiming novelty for the individual control primitives and instead argues for their composition around agent definitions.

3. System architecture

Rel(AI)Build divides the control plane into three planes: authoring/distribution, compilation, and runtime governance. The authoring layer stores canonical agents, skills, knowledge shards, profiles, and workflows with content hashes; the compilation layer normalizes Markdown+YAML and emits target-specific IDE formats; the runtime-governance layer exposes deterministic CLI/MCP helpers for phase advancement, delegation receipts, trace updates, permission checks, blocklists, lockfiles, audit logs, and drift detection.

The section’s important implementation choice is modularity. The Node.js reference implementation makes the CLI the authoritative governance path while also exposing MCP operations inside the IDE. Persistent artifacts include phase-state.json, trace.json, spec.md, handoff.md, a per-project lockfile, and an audit log. This artifact model is one of the most reusable pieces for independent harness design.

4. Governance mechanisms

The governance section is the technical core. Agent definitions are managed like software dependencies using SHA-256 content addressing, HMAC-stamped lockfiles, and hash-chained JSONL audit logs. Permission tiers define fail-closed tool allowlists and path scoping; scribe agents are path-restricted with traversal defense, while operations and specialist tiers receive controlled shell/tool capabilities. Attack-derived regular-expression blocklists cover patterns such as auto-confirmed package execution, pipe-to-shell installs, detached process spawning, persistence paths, and git configuration/hook manipulation.

The later subsections add tokenization normalization, Jaccard similarity drift zones, an eight-phase lifecycle with four human review gates, a three-iteration auto-fix cap, security-scan gates, and acceptance-criterion traceability. The strongest caveat is stated in the traceability subsection: file-to-AC linkage is cooperative. If an agent edits files without calling trace-update, the control plane detects scope creep at the next drift check but cannot prevent the edit before it lands.

5. Threat model and compliance framing

The threat model assumes adversaries may influence task inputs, shared agent-system directories through pull requests, dependency suggestions, or workspace content in untrusted repositories. Seven threats are mapped to deterministic mitigations: prompt injection, privilege escalation, context poisoning, credential leakage, uncontrolled recursion, confused deputy behavior, and workspace trust/git-hook injection.

The section is careful about residual risk. Prompt injection remains medium risk because a malicious instruction that appears AC-compliant could pass automated checks and rely on human review. Context poisoning and workspace trust are reduced but not eliminated. The compliance subsection maps mechanisms to NIST AI RMF functions and argues that agent configurations can be understood as SBOM-like artifacts because they propagate across repositories as undeclared shared components.

6. Implementation conformance testing

The conformance study asks whether the reference implementation rejects constructed bad inputs. The corpus contained 237 canonical agent definitions across 14 technology stacks and seven target IDE formats. Violations were injected by tampering with resource content after checksum recording, adding disallowed tools to low-privilege agents, and constructing shell/path strings intended to match the blocklist.

All 237 definitions compiled across targets. The injected violations were caught by their matching gates: 10 integrity tampering cases, 15 over-privileged declarations, and 20 synthetic blocklist strings. This is useful as implementation assurance but not as effectiveness evidence; the paper correctly notes that hand-written detectors catching hand-constructed inputs do not estimate real-world attack detection, usability, or developer outcomes.

7. Empirical prevalence study

The prevalence study analyzes 10,008 public GitHub repositories across 9,357 organizations, with 373 ingestion failures. It measures version-control depth, exact and near clone propagation, credential patterns, and permission-scope declarations. File-level metrics are treated as primary for maintenance depth because repository-level summaries can understate copied config-file behavior.

Key results: 58.45% of AI agent config files had exactly one commit; 74.26% had two or fewer commits; exact duplicates appeared in 18.75% of tracked config paths raw and 10.06% fork-adjusted; 75.51% of clone pairs crossed organizational boundaries; approximately 3.18% of repositories had a credential-pattern hit; only 31 of 6,145 agent config files had true-positive explicit permission declarations. The duplicate-propagation result is the most robust; permission and credential results are more fragile because parser and regex validation remain limited.

8. Limitations

The limitations section is unusually important because it defines the trust boundary. The system does not solve prompt injection, does not provide adversarial-grade signing with the default local HMAC, does not prevent unregistered edits before they land, does not secure model-provider infrastructure, and does not verify semantic correctness of generated code. Blocklists require active maintenance and cover known incidents, not novel attack families.

Runtime enforcement also varies by substrate. Claude Code has explicit session-start tool allowlist and hook behavior; Cursor offers partial runtime coverage through scoping and shell hooks; several targets may declare permissions without enforcing them at runtime. Therefore, the compiler can preserve declared governance intent, but organizations still need independent validation of each harness’s actual enforcement behavior.

9. Future work

Future work focuses on three missing validation layers. First, the Jaccard drift thresholds need calibration against behavioral change: does HIGH drift predict task-success degradation or risk increase? Second, the developer study needs randomized cohorts, controlled harnesses, pinned environments, and a bare-harness comparator to measure time-to-merge, post-merge bugs, review burden, and scope creep.

Third, the corpus analysis needs expansion, multi-threshold sensitivity for near-clone detection, improved fork metadata, and manual validation of credential-scanner hits. These are the right next steps because they separate architectural plausibility from empirical claims about safety, productivity, and prevalence.

10. Conclusion and data availability

The conclusion restates that coding-agent configuration and process artifacts lack the governance discipline applied to application code and CI/CD pipelines. Rel(AI)Build demonstrates that supply-chain integrity, pre-execution permissions, blocklists, and phase-gated traceability can be implemented as deterministic controls above existing harnesses.

The authors provide a dataset, SQLite store, analysis pipeline, figures, article source, and ancillary files through Zenodo and arXiv. This improves reproducibility for the prevalence portion, although the reference implementation’s field behavior still requires controlled studies.

FIGURE 3 — Agent-definition install pipeline

PURPOSE:
  Show how installation blocks tampering and credential leakage before transformed IDE files are written.

FLOW:
  1. Fetch resource from registry with expected SHA-256.
  2. Recompute SHA-256.
     - If mismatch: abort install; context-poisoning blocked.
     - If verified: continue.
  3. Run credential scan across 13 patterns.
     - If pattern found: abort install; credential leakage blocked.
     - If clean: continue.
  4. Write transformed IDE files.
  5. Stamp HMAC over lock data.
  6. Append action/user/timestamp/details with SHA-256 to audit log.

APPRAISAL:
  Good defense-in-depth for accidental/tamper detection, but default HMAC is not adversarial-grade against same-user compromise.

Major strengths

  • Determinism is correctly scoped: the paper does not ask an LLM to police an LLM. It uses ordinary code for hashing, permission checks, blocklists, state transitions, and drift scoring.
  • Good separation of claims: architecture, conformance tests, prevalence study, and the DRIFT vignette are not blended into one overstated evaluation.
  • Buildable artifact model: phase-state.json, trace.json, lockfiles, audit logs, canonical registry entries, and compiler targets provide concrete implementation hooks.
  • Reusable security framing: treating agent definitions as supply-chain artifacts is a strong conceptual move for enterprise agent governance.
  • Transparent limitations: the paper explicitly states that prompt injection, cooperative trace linkage, runtime enforcement disparities, and developer outcomes remain unresolved.

Major limitations

  • Outcome evidence is absent: no randomized developer study, no measured productivity benefit, no defect reduction, no incident reduction, and no real-world attack-detection estimate.
  • Traceability depends on the agent: the AC/file/test trace is auditable but not fully enforceable before edits occur unless paired with stronger file-system or git-layer controls.
  • Runtime enforcement varies by target: compiling a permission declaration does not guarantee the receiving IDE or CLI harness will enforce it.
  • Drift thresholds are unvalidated: Jaccard zones are useful for triage, but the relationship between lexical drift and agent behavior is not established.
  • Prevalence proxy fragility: exact duplicate propagation is robust, but credential and permission findings depend on regex/parsing assumptions and limited validation.

Implementation and practice takeaways

Build first
Canonical agent registry

Create one canonical definition for each agent with explicit fields for role, allowed tools, file scopes, model profile, skills, knowledge shards, and version/content hash.

Guard first
Pre-execution checks

Fail closed before the harness runs: hash mismatch, over-privileged tool declarations, disallowed paths, dangerous shell patterns, credential patterns, and missing required receipts.

Trace explicitly
Requirement → file → test

Use a structured trace artifact for acceptance criteria, implementing files, verifying tests, and status. Treat missing trace as a blockable release defect.

Do not overtrust
Cooperative trace is weak

Pair agent-reported trace updates with git-diff reconciliation, test discovery, code-owner checks, or file-system policy enforcement where possible.

Portability
Compile, then verify

Compiling to multiple harness formats is useful, but each emitted target needs parser-recovery tests and runtime enforcement validation.

Drift
Use as triage only

Jaccard drift can identify large lexical changes, but it will miss small high-impact tokens and should not be treated as semantic safety assurance.

Suggested harness-control checklist

LOCAL AGENT CONTROL PLANE CHECKLIST

SOURCE CONTROL
  [ ] Canonical agent definitions are versioned.
  [ ] Each definition has SHA-256 content hash.
  [ ] Dependency-like relationships are explicit: skills, knowledge, profiles, workflows.

INSTALL GATES
  [ ] Hash mismatch blocks install.
  [ ] Credential patterns block install or require explicit override.
  [ ] Permission tier violations fail compilation.
  [ ] Path traversal and out-of-scope writes fail closed.

RUNTIME GATES
  [ ] Shell commands pass pre-exec blocklist.
  [ ] File writes pass path policy.
  [ ] High-risk git operations are separated and reviewed.
  [ ] Security scan is recorded before phase closure after file-writing delegations.

PROCESS STATE
  [ ] Phase state is persisted in a machine-readable file.
  [ ] Start/end ordering is enforced by code.
  [ ] Delegation receipts are required for relevant phases.
  [ ] Auto-fix loops have a hard cap and escalation path.

TRACEABILITY
  [ ] Each AC links to changed files and verifying tests.
  [ ] Unlinked changed files trigger scope-creep warnings.
  [ ] Missing test traces block finalization or merge.
  [ ] Human review gates review trace completeness, not just code diffs.

PORTABILITY
  [ ] Canonical definitions compile to each target harness.
  [ ] Target parser-recovery confirms permissions and paths survived compilation.
  [ ] Runtime enforcement is tested per harness, not assumed.
