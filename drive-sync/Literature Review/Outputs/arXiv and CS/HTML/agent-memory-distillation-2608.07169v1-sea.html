One-page synthesis

Verdict: Read first. AMD is a high-value design paper for agent-memory systems because it converts a vague idea—“give the small model the teacher's memories”—into a concrete granularity-and-timing architecture, then backs that design with multi-benchmark ablations. The most reusable result is not merely the headline accuracy gain; it is the evidence that memory representation, granularity, retrieval count, and injection timing must be matched to student capacity.

Core thesis

The authors argue that small agents cannot exploit memory as effectively as large agents because they generate too few successful trajectories and because naive transfer of a stronger teacher's high-level memories remains too difficult for the student to operationalize. Agent Memory Distillation (AMD) addresses the capability gap by decomposing teacher experience into three complementary memory types: Workflow memory for task-level planning, Subtask memory for concrete intermediate execution patterns, and Function memory for reactive correction of tool-call failures.

Across four 4B–8B student models, the paper reports mean absolute gains over zero-shot of 27.2 percentage points on AppWorld, 11.2 points on BFCL V3, and 3.4 points on ToolSandbox. The strongest mechanistic finding is that Subtask memory contributes the largest incremental benefit on complex long-horizon tasks; k=1 retrieval is near-optimal; and representation should vary by level—natural language for high-level workflow, concrete code/examples for subtask and function execution.

Section condensation

1. Introduction

The paper frames small-agent memory as a two-part problem. First, small models have lower task success rates, so self-generated memory stores contain too few successful trajectories. Second, simply importing memory from a stronger teacher is insufficient because high-level teacher guidance may assume capabilities or procedural knowledge that the student lacks. The authors position this as an analogue of the teacher–student capability gap in conventional knowledge distillation, compounded by weaker in-context learning and instruction following in smaller models.

AMD's contribution is a training-free transfer scheme that makes teacher experience more executable for the student by representing it at multiple granularities and injecting it at different times. Workflow and Subtask memories are proactive; Function memory is reactive. The paper claims this is the first systematic study of teacher-to-student memory distillation designed explicitly around the capability gap; that priority claim is an author claim rather than independently verified here.

2. Related Work

The authors distinguish AMD from agent-memory methods such as Reflexion, ExpeL, AWM, ReasoningBank, MemP, ReflecTool, and SASM. Their argument is that prior memory work largely assumes a capable model using its own or similarly structured memories, whereas AMD asks how to make a stronger teacher's experience usable by substantially smaller students. SASM is the closest granularity-oriented comparator, but it uses a uniform subtask-level memory rather than separate planning, execution, and error-recovery stores.

They also separate AMD from parameter-updating knowledge distillation methods such as SAD, Agent Distillation, and SCoRe. AMD transfers behavior at inference time through memory rather than updating weights. This places it closer to test-time knowledge transfer and experience reuse than to conventional model compression, with the practical attraction that a student can change behavior without retraining.

3. Agent Memory Distillation

The formal setting is a multi-turn tool-use environment. A large teacher agent generates trajectories over a task set; only successful trajectories are used to build a memory store. Workflow memory stores a generalized task query and short natural-language strategy with tools, prerequisites, decision rules, validation cues, failure patterns, and placeholders for dynamic values. Subtask memory segments a successful trajectory into semantically coherent units, each with a label, description, concrete tool/code execution, and observations. Function memory indexes successful individual function calls by function name and preserves the call, local context, and optionally the API schema.

Retrieval follows the same hierarchy. At task start, the student retrieves top-k Workflow memory using the task instruction and independently retrieves one Subtask memory for each decomposed subtask label, deduplicating repeated hits. During execution, Function memory is retrieved only after a tool error and is appended as targeted corrective context. The main experiments use k=1, a similarity threshold, and OpenAI text-embedding-3-small embeddings. This split between proactive planning/exemplar context and reactive local repair is the paper's central architectural contribution.

4. Experiment

AMD is evaluated on three tool-use benchmarks: AppWorld test_normal (168 tasks; stateful Python API interactions across simulated apps), BFCL V3 multi-turn base (200 tasks; structured function calling with correct state and minimal viable path requirements), and ToolSandbox base (129 scenarios; conversational stateful tools scored by milestones and minefields, with GPT-5-mini as user simulator). GPT-5-mini is the main teacher. Students are Qwen3-4B, Gemma4-E4B, Qwen3-8B, and Llama3.1-8B.

The primary comparators are zero-shot, ReasoningBank, MemP, and SASM. Memory baselines are generated from the same teacher trajectories and used under their respective protocols. The paper reports two-run averages for the main experiments; a later appendix repeats zero-shot and AMD five times for Qwen3-4B. Qwen3 thinking mode is disabled, student inference is served with vLLM, and all students have a 40-step limit.

4.2 Main results

AMD improves every reported student/benchmark pair over zero-shot. The largest gains occur on AppWorld: +34.52 points for Qwen3-4B, +29.77 for Gemma4-E4B, +26.19 for Qwen3-8B, and +18.45 for Llama3.1-8B. On BFCL V3 the gains are +23.00, +8.75, +7.50, and +5.50, respectively; ToolSandbox gains are smaller (+3.88, +3.49, +5.42, +0.77). Several AMD students match or exceed the main GPT-5-mini teacher score on AppWorld or BFCL V3.

The paper also reports reduced interaction steps. On AppWorld, Qwen3-4B requires 23.8 turns zero-shot versus 10.1 for the teacher and 14.9 with AMD. The authors interpret this as transfer of efficient behavior, not only final correctness. On BFCL V3, where turn counts were already closer to the teacher, AMD changes interaction length less.

5. Analysis

Ablations establish a clear hierarchy. Workflow memory produces a consistent planning benefit, but Subtask memory supplies the dominant incremental gain on long-horizon AppWorld tasks. Function memory is usually additive but smaller and can be harmful when the model cannot absorb additional reactive context. Student-generated memory is substantially weaker than teacher memory on AppWorld, supporting the premise that small models' own successful experience is too sparse or unreliable.

Teacher quality is not sufficient by itself: for Qwen3-8B, student performance tracks teacher accuracy, but for Qwen3-4B, GPT-5-mini yields 49.40% despite lower teacher accuracy than GPT-5.5 and DeepSeek V4 Pro, suggesting teacher–student compatibility. Student-size analysis finds absolute AMD accuracy rising from 1.7B through 14B, while gain peaks at 4B. Retrieval-count and representation ablations further show that small students benefit from selective rather than broad retrieval and from code-centric execution memories rather than all-text memory.

6. Conclusion and stated limitations

The authors conclude that hierarchical memory can provide a training-free route for transferring stronger-agent experience into smaller students and that matching memory complexity to student capacity is critical. Their proposed hierarchy maps high-level planning to prose, intermediate behavior to concrete execution traces, and low-level errors to targeted function examples.

The paper explicitly limits its claims to text-based tool-use benchmarks; multimodal and open-ended coding settings are untested. Memory is generated offline and frozen, so AMD does not learn from new student successes/failures at test time or adapt to distribution shift. The framework remains dependent on suitable teacher trajectories, and adaptive teacher selection is left open.

Appendix: robustness and implementation

The most important appendix result addresses a potential evaluation concern: in the main protocol, memory is distilled and evaluated within the same benchmark task pool. The authors therefore report 7:3 cross-split evaluation and self-excluded retrieval in which each evaluation task cannot retrieve memory distilled from itself. Gains remain monotonic across memory levels, and full AMD reaches 41.07%/30.65%/22.92% on AppWorld/BFCL/ToolSandbox in cross-split evaluation and 46.43%/31.00%/23.26% under self-exclusion.

Five-run Qwen3-4B experiments show low run-to-run variability: AMD 49.60±0.91 on AppWorld, 38.67±0.58 on BFCL V3, and 20.16±0.78 on ToolSandbox. The appendix also provides the exact inference algorithm, workflow-memory generation prompt, semantic subtask segmentation prompt, student subtask decomposition prompt, and representative memory examples, making the architecture substantially more reproducible than the main text alone.

Algorithm 1 — AMD student inference

Inputs: task s; student decomposer/coder; Mwf, Mst, Mfn; k; similarity threshold δ; max subtasks N.

1. Retrieve Workflow memory with s; inject if above threshold.
2. Student decomposes s into ≤N ordered subtask labels.
3. Retrieve top-k Subtask entries per label; deduplicate; inject.
4. Execute student tool-use loop.
5. If the previous observation is an error:
      extract failing function name(s)
      retrieve Function memory by function name
      generate next action with targeted Function hint
   else:
      generate next action without Function hint
6. Execute action; append action and observation.
7. Stop on task completion or maximum steps.

Failure modes exposed by the algorithm: decomposition quality controls Subtask retrieval; embedding threshold controls false-positive memory; errors must be detectable and attributable to function names for reactive memory to activate; Function guidance does not address silent semantic errors unless an execution failure occurs.

Evaluation & appraisal

Bottom line: benchmark-useful and build-useful; not yet deployment-valid. The paper offers a credible architecture and unusually informative ablations for how small agents consume memory. The evidence supports “hierarchical, capacity-aware memory helps on these tool-use benchmarks” much more strongly than it supports universal teacher-memory distillation or production-agent claims.
9/10
RelevanceDirectly addresses small-agent memory, tool use, retrieval granularity, and training-free capability transfer.
Evidence basis: three tool-use benchmarks, four student models, memory ablations. Limiting factor: no real-world deployment. Would raise: live-agent or domain-specific validation.
8/10
NoveltyThe key novelty is not memory itself but the three-level representation plus proactive/reactive injection schedule targeted to student capacity.
Evidence basis: explicit comparison to flat/hierarchical baselines and representation/timing design. Limiting factor: components draw on known workflow, subtask, and tool-memory ideas. Would raise: broader evidence that the hierarchy is the uniquely effective decomposition.
7/10

Limiting factor: main Table 1 averages only two runs; complete memory-baseline rows are not displayed for all students; benchmark task pool is reused in the main memory construction protocol. Would raise: larger repeated trials, full comparator matrix, preregistered/equally tuned baselines.
7/10

Limiting factor: limited uncertainty reporting outside the five-run Qwen3-4B appendix and benchmark-only endpoints. Would raise: confidence intervals across all models, statistical comparisons, independent replication.
6/10
External validityThree benchmarks cover different tool-use styles, but all remain structured text/tool environments.
Limiting factor: no multimodal, open-ended coding, long-running, distribution-shift, or real-user environment; memory is frozen. Would raise: cross-domain transfer, changing tools, longitudinal memory, deployment studies.

Limiting factor: similarity threshold values, end-to-end cost, token overhead, latency, storage growth, and production governance are not fully characterized. Would raise: released code/configs with cost/latency and memory-maintenance measurements.

Strengths

  • Mechanistic ablations are unusually useful: they isolate memory type, teacher, student size, retrieval count, and representation format rather than reporting only a monolithic benchmark win.
  • Disjoint evaluation addresses the most obvious leakage concern: gains persist when evaluation tasks cannot retrieve memory distilled from themselves.
  • Negative results are informative: more retrieval degrades performance; Function memory can hurt Llama3.1-8B; stronger teacher accuracy does not always transfer better to the weaker student.
  • Implementation is concrete: prompts, examples, algorithmic control flow, top-k defaults, error-triggered retrieval, and segmentation rules are provided.
  • The architecture has a clear cognitive/computational rationale: abstract planning is encoded in prose, execution in concrete examples, and local repair in function-specific evidence.

Limitations and risks

  • Main-protocol task-pool overlap: teacher memory is originally built from the same benchmark task set used for evaluation. The appendix mitigates but does not erase the fact that the headline Table 1 numbers use the easier protocol.
  • Displayed baseline completeness: Table 1 omits ReasoningBank/MemP/SASM rows for Qwen3-8B and Llama3.1-8B, weakening the literal breadth of the “all baselines in every model” claim.
  • Uncertainty is thin: main results are two-run averages without confidence intervals; five-run standard deviations are reported only for Qwen3-4B zero-shot versus AMD.
  • Benchmark-to-deployment gap: AppWorld/BFCL/ToolSandbox do not test production concerns such as tool/API drift, security boundaries, adversarial or poisoned memory, user-specific privacy, auditability, or long-term memory maintenance.
  • Reactive Function memory depends on explicit errors: silent semantic mistakes may not trigger the corrective pathway; the appendix itself contains examples of silent wrong-key behavior, illustrating this boundary.
  • Offline frozen memory: there is no lifecycle policy for accepting new student experience, resolving conflicts, revoking stale memory, or adapting to distribution shift.
  • Cost and context tradeoffs are undermeasured: the paper shows that extra memory can hurt accuracy but does not provide comprehensive token, latency, or dollar-cost accounting.

Claim calibration

ClaimAssessment
Hierarchical teacher memory improves small-agent accuracy on the tested benchmarks.Well supported. Improvements are broad and persist under disjoint evaluation.

Confidence in appraisal: moderate-high. The paper is unusually transparent about architecture and ablations, and the appendix adds important robustness checks. Confidence is capped by preprint status, benchmark-only evaluation, partial uncertainty reporting, and lack of independent replication or deployment evidence.

Implementation takeaways

1. Match representation to abstraction.Use prose for task-level strategy; preserve executable traces/examples for intermediate and function-level behavior.
2. Separate proactive from reactive memory.Inject planning and subtask exemplars before execution; reserve detailed function guidance for error recovery to limit context inflation.
3. Default to narrow retrieval.AMD's k=1 result argues for high-confidence retrieval over memory breadth when the student is capacity-limited.
4. Treat student capacity as a policy input.Do not assume a fixed memory package works across models; additional context can decrease accuracy.
5. Evaluate memory on disjoint tasks.Same-task memory construction can overstate generalization. Self-exclusion or explicit memory/evaluation splits should be a standard evaluation condition.
6. Track teacher compatibility, not only teacher score.Teacher selection may need to optimize transferability to a particular student rather than raw teacher benchmark accuracy.
7. Preserve failure context in function memory.A bare API schema is less informative than a successful call plus the context explaining why it was used and how the response was parsed.
8. Add lifecycle controls before production.A production implementation would need stale-memory revocation, conflict handling, provenance, versioning, poisoning resistance, privacy boundaries, and monitoring—none are supplied by AMD itself.
Build-useful abstraction: AMD can be reduced to a general design rule: retrieve the minimum amount of teacher experience necessary at the level where the student's current uncertainty occurs. High-level uncertainty gets a workflow; execution uncertainty gets an exemplar; tool-interface failure gets a function-specific repair.
Do not overclaim: the paper does not show that hierarchical memory replaces training, that it improves arbitrary small models in arbitrary agent environments, or that students “become as capable as” the teacher. It shows substantial task-specific transfer in three structured tool-use benchmarks.
