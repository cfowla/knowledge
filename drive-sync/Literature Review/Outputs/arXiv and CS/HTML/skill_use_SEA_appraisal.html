One-page synthesis

Verdict: Read first. This is directly relevant to skill-based agent design, harness evaluation, reliable tool use, and the design of project-level SKILL.md workflows. Its most important contribution is not a new model but a process-level decomposition of skill use into recognition, execution, and restraint.

Core thesis

Providing an agent with a skill library does not establish that the agent can use those skills reliably. The paper argues that skill use must be evaluated as a staged process: the agent must recognize that a skill applies and retrieve it under progressive disclosure; then it must follow the prescribed procedure; and it must avoid explicitly forbidden actions. SKILL-USE operationalizes those stages as Trigger, Compliance, and Boundary.

What the study did

The authors curated 79 real skills and paired them with 177 executable tasks across nine domains. Each task runs in an isolated Docker environment, exposes only skill metadata initially, logs the execution trajectory, and is scored with a hidden multi-item rubric. Eight LLMs were tested under Claude Code and Codex harnesses. The benchmark separates skill-use scoring from ordinary task-completion scoring and gates execution credit on successful skill retrieval.

Most important results

GPT-5.5 under Claude Code, on the paper's gated Skill-Use metric.

Harness dependenceScores and rankings changed across Claude Code and Codex; skill use behaved as a model–harness property rather than a model-only capability.

Interpretive bottom line

The benchmark supports three practical conclusions. First, progressive disclosure introduces a recognition bottleneck that is distinct from procedure following. Second, partial or incorrect skill use can reduce task completion relative to giving the model no skill library. Third, reliable in-scope execution does not guarantee appropriate restraint on out-of-scope tasks. A production system therefore needs explicit instrumentation for skill selection, skill retrieval, procedure adherence, and non-applicability—not merely final-answer evaluation.

Section-by-section condensation

Abstract

The paper identifies a gap in existing skill benchmarks: most evaluate the quality of a skill artifact or its effect on task success, but not whether an agent autonomously recognizes a relevant skill, retrieves its full procedure, and follows it. SKILL-USE is introduced to evaluate this full process under progressive disclosure.

The benchmark contains 79 skills and 177 tasks in nine domains. Across eight LLMs and two harnesses, the best SU score is 0.613. The abstract's central claim is that reliable skill use remains unsolved and is conditioned by the agent harness.

1. Introduction

The introduction frames skills as structured documents specifying applicability, procedure, permitted tools, and restrictions. Progressive disclosure means only a name, short description, and path are initially visible; the model must decide to retrieve the full document. Existing instruction-following benchmarks expose constraints directly, while existing skill benchmarks often preload the skill or score only outcomes.

The authors define three evaluation facets—Trigger, Compliance, and Boundary—and describe a three-stage construction pipeline: skill/task construction, trajectory-rubric construction, and end-to-end validation. Contributions include the benchmark, its construction methodology, and a cross-model/cross-harness empirical analysis.

2. Related Work

The paper distinguishes SKILL-USE from SkillsBench, SkillLearnBench, skill-library research, SLBench, and general instruction-following benchmarks. The key distinction is the combination of progressive disclosure, open-environment execution, trajectory scoring, autonomous retrieval, procedural adherence, and explicit boundary scoring.

It also treats harness design as a first-class experimental variable, citing prior evidence that harnesses can account for substantial performance variance and reverse model rankings.

3. SKILL-USE Benchmark

An instance is defined as a skill, user task, executable sandbox, and scoring rubric. The model receives the task, environment, and skill metadata, but not the full procedure. Its output includes both the execution trajectory and final artifact state. Trigger is a binary retrieval indicator; Compliance and Boundary are weighted rubric scores; SU gates the weighted execution score on Trigger and uses α=0.7 for Compliance.

The benchmark contains 1,314 rubric items, averaging 7.4 per task. The authors use skill-exclusive requirements—requirements not inferable from the prompt or generic good practice—as the attribution basis. Construction includes masked-skill screening, cross-family adversarial review, deterministic verifiers where possible, scope-restricted LLM judging otherwise, and end-to-end executability/consistency/reliability checks.

4. Experiments

Eight models from seven families were evaluated in Claude Code and Codex. Every run occurred in an isolated Docker sandbox. Metrics included Trigger, Compliance, Boundary, gated SU, and conditional metrics restricted to triggered traces. GPT-5.4 at temperature 0 judged rubric items that were not deterministic.

The experiments examine overall performance, category differences, native versus preloaded skill injection, library-size scaling, out-of-scope restraint, the relationship between SU and task completion, cross-harness behavior, judge robustness, and sensitivity to the SU weighting parameter.

5. Conclusion

The conclusion reiterates that no tested configuration achieved reliable skill use across all three dimensions. Retrieval under progressive disclosure is highlighted as a principal gap, while out-of-scope restraint remains distinct from successful in-scope execution.

The authors release the benchmark and construction pipeline as infrastructure for training and evaluating agents that use skills more reliably.

Appendices A–G

The appendices provide benchmark comparisons, the four-phase skill-selection funnel, task and rubric design rules, human quality audit, runtime and trace-validation details, cross-harness and injection analyses, library scaling, out-of-scope behavior, robustness and weight sensitivity, review/judge prompt templates, and an ethical statement.

These appendices materially strengthen methodological transparency. They also expose important limits: LLM judges remain noisy, the benchmark relies on author-created tasks/rubrics, and the tested environments and harnesses are finite samples of the broader agent ecosystem.

Benchmark framework

Progressive-disclosure evaluation workflow

Inputs
User task, sandbox, skill name, short description, and file path.
Hidden initially
The full skill procedure and the scoring rubric.
Agent decision
Determine whether the skill is applicable and retrieve it.
Execution
Use tools, read/edit files, and produce a terminal artifact.
Recorded evidence
Full trajectory plus final artifact state.
Scoring
Trigger, Compliance, Boundary, and independent task-outcome items.
Failure modes
No retrieval; shallow retrieval without compliance; prohibited shortcuts; correct procedure with poor outcome; good outcome without skill use.

Metric definitions

Trigger:
g(y; s) = 1 when the target skill is retrieved in the trajectory; otherwise 0.

Compliance:
C(y) = weighted fraction of required skill procedures satisfied.

Boundary:
B(y) = weighted fraction of prohibited behaviors successfully avoided.

Skill-Use:
SU(y) = g(y; s) × [0.7 × C(y) + 0.3 × B(y)]

The trigger gate prevents an agent from receiving skill-use credit for behavior that happens to resemble the skill without actually retrieving it. Task outcome is measured separately, avoiding conflation between “used the skill correctly” and “completed the task.”

Three-stage benchmark construction pipeline

  1. Skill and task construction: curate real skills, screen for skill-exclusive and observable requirements, and build executable in-scope tasks using real assets.
  2. Rubric construction: define evaluability gates, Compliance/Boundary items, and independent task-outcome items; prefer deterministic checks.
  3. End-to-end validation: verify executability, cross-component traceability, and rubric reliability through replay and adversarial review.

Injection mode

Preloading the full skill consistently improved Trigger and therefore SU, especially for models with weak native retrieval. When analysis was restricted to cases that triggered under both modes, execution scores remained near the diagonal, indicating that preloading primarily solved recognition rather than procedure-following.

Skill-library scaling

The largest degradation occurred when moving from one skill to a ten-skill library. Additional growth to 20 or 30 skills caused comparatively little further decline. Most failures were no-skill outcomes rather than selection of a wrong distractor, suggesting an entry or recognition cost rather than escalating confusion among many skills.

Out-of-scope restraint

Within-scope SU and out-of-scope avoidance were negatively rank-correlated in the reported analysis. Models that used skills strongly in applicable tasks could still over-trigger them for topically related but procedurally irrelevant tasks. This is a major safety and workflow-design concern.

Task completion

Paired task-completion gain shifted from negative to positive at approximately SU=0.5. Below this point, partial skill use often harmed performance relative to a no-library baseline; above it, the skill acted as a useful scaffold. This is one of the paper's most operationally important findings.

Robustness and sensitivity

Repeated LLM-judge scoring preserved the broad leaderboard but showed moderate item-level noise, concentrated in mid-range traces. Compliance was the most stable continuous component. Model rankings were stable for compliance weights α from 0.5 to 0.75, so the default α=0.7 was not the primary driver of conclusions.

Appendix Table 2 — Benchmark positioning

SKILL-USE is presented as the only compared benchmark combining an open environment, trajectory/process scoring, progressive-disclosure skill documents, and separate Trigger, Compliance, and Boundary dimensions. This positioning is persuasive within the comparison set, though it remains dependent on how benchmark features were categorized.

Appendix Tables 3–5 — Selection funnel and rubric governance

The selection funnel applies repository-quality filters, fetch quotas, rule-density/style scoring, and masked-skill evaluation. Rubric governance restricts LLM judges to one binary item at a time, item-specific evidence, and adjudication. Guideline rules are tied to concrete prior failures, including absolute-path leakage, reference artifacts visible at runtime, narration-matching regexes, and catastrophic backtracking.

Appendix Tables 6–10 — Harness agreement, weighting, out-of-scope cases, and judge stability

Cross-harness task-level correlations were stronger for leading models and weaker for several middle-tier open models. Weight sensitivity did not materially change the rankings across α=0.5–0.75. Out-of-scope errors concentrated in a small set of ambiguous tasks. Repeated-score reliability was moderate rather than high, with ICC(2,1) reported as 0.530 for SU, 0.604 for Compliance, 0.471 for Boundary, and 0.478 for task completion.

Evaluation and appraisal

Relevance
10/10

Directly addresses skill invocation, progressive disclosure, harness effects, and reliable procedural execution.

Evidence basis: benchmark target and experiments. Limiting factor: not tailored to clinical or CDS workflows. Would rise: already at ceiling for agent-skill research.

Novelty
8/10

The Trigger–Compliance–Boundary decomposition and gated process-level evaluation provide a useful distinction from outcome-only skill benchmarks.

Limiting factor: components overlap with retrieval, instruction-following, and SOP-adherence ideas. Would rise: stronger theoretical validation or broader independent adoption.

Method strength
8/10

Executable tasks, isolated sandboxes, trajectory rubrics, masked-skill checks, adversarial review, human audit, and multiple ablations form a strong benchmark methodology.

Limiting factor: author-created tasks/rubrics and partial dependence on LLM judges. Would rise: independent reproduction and preregistered benchmark governance.

Evidence strength
7/10

The empirical claims are supported by broad benchmark runs and targeted analyses, with quantitative reporting and robustness checks.

Limiting factor: benchmark-only evidence, moderate judge reliability, and no external deployment study. Would rise: repeated independent evaluations and real-world trace validation.

External validity
6/10

Nine domains and two harnesses provide useful diversity, but the tasks, skills, model versions, and harness implementations remain a limited sample.

Limiting factor: controlled Docker tasks may not reflect long-running, multi-user, permissioned, or high-stakes systems. Would rise: more harnesses, organizations, live workflows, and longitudinal evaluation.

Implementation value
9/10

The paper offers immediately reusable evaluation concepts, task-construction controls, rubric architecture, and monitoring metrics.

Limiting factor: operational adoption still requires local task and verifier engineering. Would rise: stable reference implementation and standardized trace schema.

Main strengths

  • Defines skill use as a process rather than inferring it from final task success.
  • Separates recognition, required execution, and prohibited behavior.
  • Uses trajectory evidence and final artifact state rather than self-reported intent.
  • Explicitly tests harness dependence rather than treating model capability as invariant.
  • Includes masked-skill screening to reduce credit for generic engineering practice.
  • Provides unusually detailed construction, validation, and judge-governance appendices.

Main limitations

  • The paper is a v1 preprint and the results have not yet been independently replicated in the supplied source.
  • Benchmark creators also design the tasks, rubrics, and many verifier choices, creating potential construct and authoring bias.
  • LLM-judge reliability is moderate, particularly for Boundary and task-completion items.
  • Only two harnesses are tested; conclusions about harness dependence are convincing but not exhaustive.
  • Models and harnesses are version-sensitive, so the numeric leaderboard may age rapidly.
  • Task domains are broad, but ecological validity for enterprise governance, clinical CDS, and other high-stakes workflows is not established.
  • The benchmark measures whether skills are used as written, not whether the skills themselves encode correct, safe, or current procedures.
Do not overclaim. A high SU score would show reliable use of the benchmark's supplied procedures. It would not establish that the procedures are correct, that the agent is generally safe, or that it will remain reliable after model, tool, policy, or harness updates.

Confidence in appraisal

Moderate to high. The primary PDF provides detailed methods, quantitative results, appendices, and limitations sufficient for a strong internal appraisal. Confidence is below “high” because this assessment did not independently run the released benchmark, inspect the current repository, or verify post-v1 corrections.

Implementation and project takeaways

1. Treat skill use as a staged contractLog and score applicability decision, retrieval, procedure steps, prohibited actions, and final outcome separately. A single pass/fail result hides the dominant failure mode.
2. Preserve progressive disclosure testsPreloading every skill may improve benchmark performance but removes the key test of autonomous recognition. Evaluate both native and preloaded modes.
3. Build skill-exclusive testsOnly score behaviors that arise from the skill rather than the task prompt or generic best practice. Use masked-skill baselines to identify non-exclusive requirements.
4. Separate structural and semantic verificationUse deterministic checks for tool calls, paths, file state, ordering, and prohibited commands; reserve LLM judging for requirements that cannot be expressed reliably.
5. Add out-of-scope negative tasksA skill system should be evaluated both for entering the correct skill and for refusing topically related but procedurally irrelevant skills.
6. Evaluate the model–harness pairDo not publish or rely on “model skill-use” scores without naming the harness, context policy, turn limits, tool schema, and injection mode.
7. Detect sham triggersTrack retrieved-skill traces with very low Compliance. Retrieval rate alone can look strong while masking shallow or abandoned execution.
8. Require minimum execution quality before deployment valueThe paper's task-completion analysis suggests partial skill use can be worse than no skill. Consider fallback to a no-skill path or human escalation when procedural confidence is low.
