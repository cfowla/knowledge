One-page synthesis

Verdict: Read first. Best use: design a skill-review pipeline that treats static inspection and sandbox execution as one evidence record tied to an exact artifact version.

TRUSS proposes an admission process for generated agent skills. The candidate package is frozen and assigned a content digest. A Checker inspects functional claims and nine safety properties, then turns unresolved but testable claims into runtime obligations. The exact admitted digest runs in a Controllable Execution Environment where brokered tools mediate side effects and preserve a causal trace. The Refiner uses artifact spans and runtime events as a revision specification. Any edit creates a new digest and restarts checking.

The benchmark results are strong inside the tested setup. TRUSS reports 100% precision, recall, and F1 on the SkillInject vulnerability-detection benchmark. On SkillSafetyBench, repair lowers attack success without reported attack regression, but residual attacks remain and safe task completion varies sharply by executor configuration. On SkillGenBench, task effectiveness is 52.94% with TRUSS versus 17.11% with no skills, and the controlled security probes report a 100% pass rate for TRUSS. These results support the workflow as a build pattern. They do not justify a general safety certificate because scenario coverage, observer coverage, and executor behavior bound what the runtime evidence can show.

Section condensation

Abstract and introduction

The paper frames automated skill generation as a joint function and safety problem. Skill instructions and executable resources can change agent behavior in ways that static text review does not fully expose, especially when failures depend on tool state or multi-step execution. TRUSS therefore treats admission as a combination of artifact inspection and controlled execution evidence.

The core claim is narrower than general agent safety. TRUSS asks whether a specific skill candidate satisfies declared functional requirements and a predefined safety contract under the evaluated scenarios. Exact artifact identity and traceability are part of that claim.

Related work

The related-work section places TRUSS between automated skill generation and agent-skill security. Existing generation methods focus on producing reusable procedures and resources, while security work identifies prompt injection, unsafe capability use, or malicious skill content. TRUSS argues that neither generation quality alone nor static vulnerability inspection captures state-dependent execution behavior.

Methodology: formulation and framework

The paper defines functional effectiveness as expected utility improvement over the same agent operating without a skill. Per-property safety risk is the expected violation indicator. The stated objective maximizes functional value while penalizing average safety risk.

The operational framework is Generator to Checker to Refiner. The Checker has static and runtime phases. The Refiner receives a Function and Safety Record that points back to the candidate artifact or execution event responsible for a failure.

Methodology: generator and static checker

The Generator emits a complete skill package and freezes it before inspection. Provenance and a content digest bind subsequent findings to that exact version. Functional inspection decomposes claims into usage conditions and observable effects, checks available evidence, and converts unresolved but executable criteria into runtime obligations.

The safety contract has nine properties covering control, access, executable provenance, lifecycle, resource budgets, evidence, authority, composition, and transactions. Static scope follows both declared behavior and implemented capabilities. Admission is digest-specific.

Methodology: runtime execution traces

The Controllable Execution Environment isolates the candidate in a disposable workspace with synthetic data and brokered external interactions. Direct command networking is disabled. An intermediate breaker checks every requested action before dispatch. Rejected requests remain in the trace as blocked events.

Functional and safety judgments use the same execution evidence. The trace preserves tool-call identity, returned observations, broker decisions, causal links, scenario identity, and skill digest through cleanup and final state. Policy-violating attempts count as violations even when blocked. Missing observer coverage leaves an obligation unresolved.

Methodology: refinement

The Refiner gets an evidence-bound failure record. Static findings identify criteria and artifact spans. Runtime findings identify requests and trace positions. Functional failures compare expected and observed state. Satisfied criteria remain preservation constraints during repair.

Every revised package receives a new digest and must pass static inspection and fresh runtime execution. If the revision budget ends before obligations are resolved, TRUSS returns an uncertified candidate with residual findings rather than silently admitting it.

Evaluation

RQ1 evaluates vulnerability detection on 84 matched clean/injected SkillInject pairs, 168 blinded artifacts. RQ2 evaluates repair on all 155 SkillSafetyBench cases using the benchmark task and attack verifiers. RQ3 evaluates generation on all 187 SkillGenBench tasks. Metrics include detection precision, recall, F1, attack success, attack elimination, attack regression, safe task completion, task effectiveness, reusability, and controlled security probes.

TRUSS reaches 100% precision, recall, and F1 on SkillInject. SkillSafetyBench repair reduces attack success from 38.71% to 19.35% for Codex plus GPT-5.5 and from 46.45% to 29.68% for Codex plus GPT-5.4, with 0% reported attack regression. Safe task completion is 52.90% and 23.87% in those two configurations. On SkillGenBench, effectiveness is 52.94% for TRUSS, 29.95% for the LLM Generator, and 17.11% with no skills. Security-probe pass rates are 100%, 75.40%, and 50.80%, respectively.

Conclusion

The authors argue that runtime evidence can expose failures missed by artifact-only inspection and provide a better basis for revision. The paper also notes that residual attack success and executor-dependent safe task completion limit what the certification claim can mean.

The stated next steps are broader scenario diversity and broader property-observer coverage. Those are not minor extensions. They define the boundary between benchmark success and stronger evidence that the workflow transfers to open-ended skill ecosystems.

Evaluation and appraisal

Relevance 9/10

Direct fit for agent-skill review and evidence-preserving admission workflows.

Evidence basis
The method centers on skill generation, verification, execution traces, and revision.
Principal limit
Evaluation is not a scientific-literature pipeline.
What would raise the score
Validation on document and research-agent skill packages would raise confidence in direct fit.

Novelty 8/10

The value is the integrated admission loop rather than any one checker.

Evidence basis
Static requirement inspection, brokered execution evidence, exact-digest provenance, and trace-linked refinement are combined in one workflow.
Principal limit
Several ingredients are established software and security patterns.
What would raise the score
Ablations that isolate each component would clarify what is genuinely additive.

Method strength 7/10

The paper uses three benchmarks, matched clean/injected artifacts, official verifiers, and more than one executor configuration.

Evidence basis
RQ1 uses 168 blinded artifacts, RQ2 uses 155 benchmark cases, and RQ3 uses all 187 SkillGenBench tasks.
Principal limit
The main paper does not provide the stated separate component ablation and gives limited uncertainty analysis.
What would raise the score
Independent replication, component ablation, and statistical uncertainty would raise the score.

Evidence strength 7/10

Reported benchmark deltas are large and internally consistent, but the strongest safety numbers come from controlled benchmarks and probes.

Evidence basis
TRUSS reaches 100% precision and recall on SkillInject and 100% security pass rate on SkillGenBench probes, while repair still leaves residual attack success.
Principal limit
No result establishes safety outside the tested properties, observers, scenarios, and executor conditions.
What would raise the score
External adversarial evaluation with broader observers and confidence intervals would raise the score.

External validity 5/10

The experiments cover several benchmarks and executor settings, but remain synthetic or benchmark-bound.

Evidence basis
The paper tests vulnerability detection, repair, and generation across SkillInject, SkillSafetyBench, and SkillGenBench.
Principal limit
Scenario coverage and executor behavior materially affect the runtime result.
What would raise the score
Production-style deployments, unseen skill ecosystems, and adaptive red-team tests would raise the score.

Implementation value 9/10

The paper specifies a concrete review architecture that can be translated into a skill QA pipeline.

Evidence basis
Content digests, static gates, runtime obligations, a brokered CEE, provenance-preserving traces, and evidence-bound refinement are described explicitly.
Principal limit
The exact implementation and observer coverage still need local design choices.
What would raise the score
An open reference implementation and fixtures for the nine properties would raise the score.

What the evidence supports

TRUSS supports the claim that an exact-version, evidence-linked static and runtime checking loop can outperform the paper's static-only and generator baselines on the tested benchmarks. It also gives a concrete way to preserve blocked unsafe attempts and functional failures as review evidence.

What the evidence does not support

The 100% benchmark results should not be read as a general safety guarantee. Safety coverage depends on the properties that were defined, the scenarios that were generated, the observers that were implemented, and the executor that ran the skill. Residual SkillSafetyBench attacks remain after repair. The accessible main paper also does not contain the component ablation it says is reported separately.

Bottom line

Best use: architecture and QA design for agent skills, especially exact-artifact provenance, brokered shadow execution, and evidence-linked repair.

Do not use for: claiming that a skill passing these checks is safe under arbitrary production conditions or adaptive attacks.

Confidence in appraisal: moderate to high for the described workflow and reported benchmark results; moderate for external transfer because the evidence remains benchmark-bound.

Implementation takeaways

Freeze first

Assign one digest to the full candidate package before review. Findings without exact artifact identity are weaker evidence.

Make runtime obligations explicit

Static uncertainty should become a named executable test, not a vague reason to run the skill and inspect whatever happens.

Keep blocked attempts

A safety broker should record policy-violating requests even when no side effect occurs. The attempted action is part of the evidence.

Use one trace for function and safety

Judge completion claims, final state, unsafe attempts, admitted actions, cleanup, and residual state from the same causal record.

Recheck after every edit

Repairs invalidate the prior digest. A revised package needs fresh static and runtime evidence.

Label the certificate narrowly

A pass means the evaluated obligations were resolved in the evaluated scenarios. Keep unknown coverage and residual findings visible.
