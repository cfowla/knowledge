Source type

Domain
Semantic query processing; claim verification; provenance; LLM cost optimization
Scope warning
System/benchmark evidence, not proof that all semantic aggregates can be verified reliably. Findings depend on the claim set, datasets, LLMs, and reference labels.

One-page synthesis

Core thesis. Semantic aggregation can produce natural-language summaries over large relations, but those summaries may contain unsupported claims. Evergreen verifies the claims by compiling each one into a declarative semantic verification query rather than asking an LLM to judge the whole relation.

Method. Evergreen decomposes aggregate text into claims, maps claims to logical structures over relations, compiles them into a constrained DataFrame-style query interface, and executes a mix of semantic LLM operators plus symbolic relational operators. It reduces LLM cost using verification-aware optimizations—early stopping, relevance sorting, and confidence-sequence estimation—and general semantic-query optimizations—operator fusion, similarity filtering, and prompt caching.

Evidence. The benchmark uses 32 production-inspired claims over Yelp restaurant reviews and Twitter customer-support datasets, with grounded and ungrounded claims balanced. Optimized Evergreen with Claude Opus 4.6 preserves F1 at 0.94 while reducing average cost from $15.88 to $5.05 versus unoptimized Evergreen; optimized Evergreen with Qwen3-VL reaches F1 0.87 at $0.183, outperforming the strongest non-Evergreen baseline F1 0.83 at $1.29.

semantic query processing enginesDatabase-style systems that add LLM-powered semantic operators to ordinary query processing so users can filter, map, aggregate, or rank unstructured/natural-language data.Evergreen assumes these engines already produced the semantic aggregate and can also execute the verification query.
semantic operatorsLLM-backed query operators, such as prompt-based filter or map, that evaluate meaning rather than only structured values.They are the expensive and error-prone part of verification, so Evergreen optimizes how often they run.
database operatorsTraditional deterministic operators such as filter, map/projection, aggregate, sort, rank, scan, and check over relations.Evergreen combines these with semantic operators so symbolic query processing handles quantifiers and groupings.
semantic aggregationAn LLM-based aggregation that reduces many tuples into a natural-language summary, comparison, ranking, or other aggregate text.The paper’s problem starts because semantic aggregates can contain unsupported claims.
primitive operatorA built-in, first-class operator in a query engine rather than an ad-hoc prompt pattern.The paper treats semantic aggregation as a primitive in emerging engines, motivating a corresponding verification mechanism.
aggregation functionThe function applied across tuples or groups, such as bool_or, bool_and, count_if, proportion, or an LLM summary prompt.Evergreen maps claim quantifiers to aggregation functions so verdicts are computed by the engine.
naive LLM-as-a-judgeA baseline that asks an LLM to decide whether a claim is supported by the available source text or serialized relation.It fails when relations exceed context windows or when quantified/grouped reasoning is better handled symbolically.
symbolic operationsDeterministic operations over structured values, counts, booleans, ranks, and comparisons.Evergreen uses them after semantic per-tuple labeling to avoid asking an LLM to count, rank, or quantify unreliably.
quantifiersLogical constructs such as exists, all, at least k, majority, proportion thresholds, and nested combinations over groups.They characterize claim types and determine which aggregates and stopping rules are appropriate.
groupingsPartitions of a relation by one or more attributes, such as business_id or airline account.Grouped verification supports ordinal and nested claims where each group needs its own aggregate.
symbolic processingQuery-engine computation over known structured values after semantic labeling.It is the part Evergreen makes exact or statistically controlled.
query-based verification systemA system that verifies claims by compiling them into declarative queries rather than free-form judging.Evergreen extends this database tradition to claims requiring semantic evaluation.
provenance captureRecording which input tuples/facts justify a verdict.Evergreen attaches citations to true and false verdicts rather than returning only a boolean.
semantic verification queryThe declarative Evergreen query compiled from a natural-language claim using relational and semantic operators.This is the central abstraction that turns claim verification into query execution.
relational operatorsOperators from relational query processing: filter, map, aggregate, sort, rank, scan, and terminal check.They provide the deterministic backbone around LLM-backed semantic predicates.
verification-aware optimizationsOptimizations tailored to boolean claim verification, including early stopping, relevance sorting, and confidence-sequence estimation.They exploit the fact that verification only needs enough evidence to settle a verdict.
general-purpose optimizationsSemantic-query optimizations not specific to verification, such as operator fusion, similarity filtering, and prompt caching.They reduce redundant or unnecessary semantic operator calls.
operator fusionCombining adjacent semantic operations into one LLM call when safe.In Evergreen, a semantic filter and semantic map over the same tuple may be fused to reduce calls.
similarity filteringA cheap embedding-based prefilter that removes tuples unlikely to satisfy a semantic filter before invoking an LLM.It trades recall risk against cost reduction; the paper uses a conservative threshold.
prompt cachingReusing outputs from repeated or equivalent LLM prompt calls.It lowers cost when multiple claims or operators ask the same semantic question over the same tuple.
semiring provenanceA formal data-provenance model where annotations are combined algebraically to represent alternative and joint explanations.Evergreen uses it to define which tuples justify claim verdicts, including false verdicts.
first-order logicA logic with predicates, variables over tuples, Boolean connectives, and quantifiers.Evergreen maps claim types over relations into this logical form.
neuro-symbolicA design combining neural/LLM semantic judgments with symbolic query execution.Evergreen restricts LLMs to semantic predicates and leaves quantifier/group/rank logic to the query engine.
verification queryA query that computes whether a claim is grounded in the underlying relation.In the paper this is the executable form of each decomposed claim.
claimA natural-language assertion extracted from a semantic aggregate about the underlying relation.Evergreen verifies claims such as “majority positive reviews” or “all locations have complaints.”
claim decompositionThe step of breaking a semantic aggregate into explicit individual claims and resolving vague references.It supplies Evergreen with concrete claims to compile and verify.
relationThe finite table-like set of tuples that the claim is about.It is Evergreen’s domain for logical quantification and query execution.
symbolic predicatesPredicates computable from structured fields without LLM semantics, such as age > 21 or business_id = A.They are cheap and deterministic parts of filters or formulas.
semantic predicatesPredicates requiring interpretation of natural language or unstructured content, such as whether a review mentions vegan options.They are evaluated by LLM-backed prompt expressions.
conjunctionLogical AND over predicates or formulas.In provenance semantics it corresponds to joint evidence, represented by multiplication.
disjunctionLogical OR over predicates or formulas.In provenance semantics it corresponds to alternative evidence, represented by addition.
negationLogical NOT.Evergreen relies on first-order provenance with dual tokens so false verdicts and negative facts can be explained.
existential claimA claim asserting that at least one tuple satisfies a predicate.Verified with bool_or or equivalent; a true verdict can stop at the first witness.
existential quantifierThe “there exists” quantifier over tuples.It models claims like “some reviewers enjoyed the chicken salad.”
universal claimA claim asserting that all relevant tuples satisfy a predicate.Verified with bool_and or equivalent; a false verdict can stop at the first counterexample.
universal quantifierThe “for all” quantifier over tuples.It models claims like “the reviews do not mention vegan options,” after translating the predicate appropriately.
cardinal claimA claim asserting a count threshold or exact count for tuples satisfying a predicate.Verified with count_if plus a comparison.
cardinal quantifierA numeric-count quantifier such as at least k, fewer than k, exactly k, or not k.It generalizes existential/universal logic in finite relations.
proportional claimA claim asserting a proportion or percentage threshold.Verified with proportion plus a comparison.
proportional quantifierA quantifier over fractions of tuples, such as majority, minority, or at least 10%.Evergreen can reduce it to a count threshold when the relation size is known.
ordinal claimA claim about rank among groups, such as the top-ranked location by service praise.Verified with grouped aggregation plus with_rank and a final check.
nested claimA claim with one quantifier inside another, often over groups.Example: all McDonald’s locations have at least two poor-service complaints.
outer quantifierThe higher-level quantifier applied across groups in a nested claim.In the example, “all locations” is the outer universal quantifier.
inner quantifierThe lower-level quantifier applied within each group.In the example, “multiple complaints” is the inner cardinal quantifier.
declarativeSpecifying what condition should hold rather than how to execute it step by step.Evergreen asks the LLM to produce a constrained query, then lets the engine optimize execution.
query interfaceThe Evergreen DataFrame-style API for composing filter, map, aggregate, rank, and check operations.It constrains the LLM compiler to valid, optimizable operations.
core operatorOne of Evergreen’s main query operators: filter, map, aggregate, with_rank, and check.These provide the minimal vocabulary for expressing verification queries.
early stoppingStopping semantic evaluation once enough evidence has been seen to confirm or refute a claim.It is the largest reported cost-saving mechanism because LLM calls dominate cost.
monotoneA property where an aggregate’s relevant value moves in one direction as satisfying tuples are observed.It enables stopping rules for counts, booleans, and proportions.
iterator modelA lazy query-execution model where operators pull tuples from child operators as needed.Evergreen uses it so upstream semantic operators are invoked only for tuples actually needed.
witnessA tuple that satisfies an existential claim or otherwise proves a positive condition.For bool_or, the first witness can settle a true existential verdict.
counterexampleA tuple that violates a universal claim or otherwise refutes a condition.For bool_and, the first counterexample can settle a false universal verdict.
accumulatorThe running state inside an aggregate, such as a count, proportion estimate, or Boolean aggregate.Evergreen checks the accumulator against pushed-down comparison conditions to stop early.
cardinality scan operatorA cheap pre-LLM scan that counts the number of input tuples.It lets Evergreen know whether remaining unseen tuples could still change a count verdict.
scanningReading/counting tuples without expensive semantic LLM evaluation.The paper treats scanning as cheap relative to LLM calls.
hash-based aggregatesAggregates that maintain hash tables for groups and generally require pulling all tuples through upstream operators.Evergreen avoids them when early stopping needs group-contiguous streaming.
group-contiguousAn input order where all tuples for the same group appear together.It lets streaming grouped aggregates finish one group and skip remaining tuple processing when resolved.
ad-hoc sensor networksPrior database setting where pushing HAVING predicates into grouped monotonic aggregates reduced expensive transmission/storage.The paper uses it as an analogy for pushing verification comparisons into aggregates.
relevance sortingOrdering tuples so likely witnesses or useful evidence appear early.It accelerates deterministic early stopping for claim types where a few satisfying tuples can confirm the verdict.
semantic mapA map operation whose expression uses an LLM prompt to produce a new semantic attribute for each tuple.Example: label whether each review complains about poor service.
semantic search queryA natural-language query used to retrieve or rank tuples by likely relevance.Evergreen uses it in relevance sorting to surface high-yield tuples before LLM evaluation.
inclusion keywordA keyword whose presence increases a tuple’s relevance score.Used with semantic search query and exclusion keywords in relevance sorting.
exclusion keywordA keyword whose presence reduces or whose absence increases relevance, depending on the ranking signal.Helps avoid tuples likely irrelevant to the claim predicate.
Reciprocal Rank FusionA ranking method that combines multiple ranked signals by summing reciprocal rank scores.Evergreen uses it to combine embedding similarity and keyword signals for relevance sorting.
estimation with confidence sequenceA probabilistic optimization that samples tuples and maintains an anytime-valid interval until a Boolean comparison is resolved.It enables early stopping without fixing a sample size in advance.
online aggregationProgressively refining aggregate estimates as more data are processed.Evergreen adapts this idea but uses confidence sequences to avoid invalid repeated peeking.
classical confidence intervalsIntervals valid for a fixed, preplanned sample size.They become invalid if repeatedly checked until they cross a threshold.
peeking problemInflated error risk caused by repeatedly checking ordinary confidence intervals during sampling.Evergreen avoids this with anytime-valid confidence sequences.
confidence sequencesSequences of confidence intervals valid simultaneously over time.They allow Evergreen to stop whenever the verdict becomes clear.
Bernoulli random variables0/1 variables indicating whether each sampled tuple satisfies a Boolean expression.They are the statistical objects used for proportion and count estimation.
anytime-valid (1-alpha)-confidence sequenceA confidence sequence that contains the true value at all sample sizes with probability at least 1-alpha.This is the guarantee that makes repeated stopping checks statistically sound.
significance levelThe alpha error probability allocated to an estimation decision.Evergreen budgets it across operators, accumulators, and groups.
confidence levelThe complement 1-alpha of the significance level.It expresses the probability target for the confidence sequence covering the true proportion.
tolerance intervalA band around a comparison threshold where approximate equality is accepted or where a verdict can be considered settled under tolerance.Used especially for equality comparisons in approximate estimation.
betting approach of Waudby-Smith and RamdasThe statistical method Evergreen uses to compute confidence sequences.It supplies the anytime-valid intervals used by the estimation optimizer.
shuffle operatorAn operator that randomizes tuple order to satisfy exchangeability assumptions for confidence sequences.Evergreen inserts it when estimation is used, while preserving group contiguity when needed.
table scanThe base operator that reads tuples from the relation.Relevance sort, shuffle, and cardinality scan are placed around scans to minimize expensive semantic calls.
sort operatorAn operator that orders tuples by group or relevance.Evergreen sorts to create group-contiguous streams and to surface likely witnesses.
family-wise error rateThe probability that any confidence sequence in a query fails to contain its true value.Evergreen controls this when multiple estimation decisions occur in one query.
Bonferroni correctionA conservative method for dividing alpha across multiple comparisons or groups.Evergreen uses it when the number of groups is known.
error budgetThe total allowed alpha allocated across estimation components.The query optimizer splits this budget so the query-level error bound holds.
positive relational algebraThe negation-free fragment of relational algebra using operations such as selection, projection, join, and union.Classic semiring provenance was originally developed for this setting before extension to negation.
commutative semiringAn algebraic structure with addition and multiplication used to combine provenance annotations.Addition represents alternatives; multiplication represents joint use of evidence.
indeterminateA variable symbol in a provenance polynomial associated with an input fact or tuple.It lets the polynomial track which tuple contributed to a result.
provenance tokenThe paper’s tuple-level annotation used as an indeterminate in provenance expressions.Tokens become citations/evidence identifiers in Evergreen verdicts.
alternativeA separate sufficient explanation for a result.Represented by semiring addition between monomials.
jointEvidence items that must be used together for one explanation.Represented by semiring multiplication inside a monomial.
alternative explanationOne monomial in a provenance polynomial: a distinct minimal set of jointly contributing tuples.Evergreen typically returns one minimal explanation rather than all alternatives.
first-order logic with negationFirst-order logic extended with NOT, enabling explanation of false as well as true statements.Evergreen relies on this to support why-not provenance for false verdicts.
positive tokenA token recording that a tuple satisfies the predicate.Used to justify true existential/cardinal/proportional claims and parts of universal claims.
dual indeterminateThe paired negative provenance variable corresponding to a positive token.It represents evidence that a tuple does not satisfy the predicate.
positive factThe fact that a tuple satisfies a semantic or symbolic predicate.Encoded with a positive token.
negative factThe fact that a tuple does not satisfy a predicate.Encoded with a negative/dual token.
interpretationA mapping from logical literals/formulas to provenance polynomials.It defines how Evergreen turns logical claim truth into explanatory tokens.
literalAn atomic predicate or its negation treated as a base unit in the provenance semantics.Evergreen treats semantic predicate results and their negations as literals.
why-provenanceExplanation of why a true result holds.Evergreen returns supporting tuple tokens for true verdicts.
why-not provenanceExplanation of why an expected or asserted result is false.Evergreen applies provenance to the negated formula to explain false verdicts.
verdictThe final boolean outcome of a verification query: the claim is grounded or ungrounded/unsupported.The check operator produces it and attaches provenance.
true existentialAn existential claim with at least one satisfying tuple.Evergreen can return the first positive witness token.
false existentialAn existential claim with no satisfying tuples.Evergreen returns negative tokens showing no relevant tuple satisfies the predicate, or a sampled subset under estimation.
true universalA universal claim where every relevant tuple satisfies the predicate.Provenance is the joint product of positive tokens over all relevant tuples, or sampled evidence under estimation.
false universalA universal claim where at least one tuple violates the predicate.Evergreen can stop at the first negative counterexample token.
true cardinalA count-threshold claim whose numeric condition is satisfied.Provenance contains enough positive or negative tokens to justify the threshold.
false cardinalA count-threshold claim whose numeric condition is not satisfied.Provenance explains the failed threshold, often by showing insufficient positives or too many negatives.
approximate query processingDatabase techniques that trade exactness for speed using sampling and statistical guarantees.Evergreen borrows AQP ideas but only needs enough precision to resolve Boolean claim verdicts.

Evaluation and appraisal

Verdict: Read first

High utility for RAG/scientific curation systems that need deterministic verification around LLM-generated summaries, especially where claims contain counts, proportions, rankings, or group-level quantifiers.

Relevance
9/10

Directly relevant to semantic verification, RAG-adjacent factuality, scientific curation, and LLM/database hybrid systems.

Limiting factor: Less directly applicable to free-form multi-hop web verification.

Novelty
8/10

Strong synthesis of semantic query processing, verification-aware optimization, and first-order semiring provenance.

Limiting factor: Builds on established database provenance and approximate query processing foundations.

Method strength
8/10

Declarative interface, executable baselines, balanced claim set, cost/latency metrics, provenance quality, and ablations strengthen the system evidence.

Limiting factor: Only 32 claims and limited domains constrain breadth.

Evidence strength
7/10

Reported cost-quality results and optimization ablations support the main claim that structured verification can dominate naive judging.

Limiting factor: Production-inspired benchmark is still small; no broad external task suite.

External validity
6/10

The abstraction should transfer to many relational/unstructured-data settings with semantic operators.

Limiting factor: Needs more domains, claim types, engine integrations, and stress tests.

Implementation value
9/10

Highly build-useful: claim decomposition, typed query compilation, early stopping, relevance sorting, confidence sequences, and provenance are directly reusable design components.

Limiting factor: Requires a semantic query engine, reference labels/evaluators, and careful threshold/error-budget engineering.

Implementation / practice takeaways

Useful architecture pattern

Let an LLM translate a claim into a constrained declarative query, then let the query engine perform optimization, counting, grouping, ranking, and provenance capture.

Best fit

Verification of LLM-generated summaries over tables, reviews, tickets, notes, or logs where claims have quantifiers, counts, proportions, groups, or ranks.

Do not overclaim

Evergreen does not eliminate semantic mislabeling by LLM operators. It narrows the LLM’s role and makes the symbolic parts reliable, auditable, and cheaper.
