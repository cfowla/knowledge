One-page synthesis

Core thesis. Long software-repair trajectories fail not only because the base model reasons poorly, but because the agent loses or misuses state. PMCoder treats planning and episodic memory as one coupled control system: plan phase/sub-task determines what memory resurfaces, memory-derived trajectory statistics can force replanning, and execution evidence can prevent verification state from advancing on self-report alone.

What changed. The system adds a deterministic hierarchical phase planner, token-budgeted MMR episodic memory with lexical + code-graph relevance, marker-delimited tool-result injection, validated issue-reproduction verdicts for verification state, and edit-integrity/revert-then-refix recovery. The planner uses only one LLM call at task start; per-step planning and retrieval are non-LLM computations.

Headline evidence. On SWE-bench Verified with Qwen3-Coder-30B-A3B-Instruct-FP8, PMCoder averaged 167.3/500 resolved (33.5%) versus 142.3/500 (28.5%) for baseline: +25.0 cases / +5.0pp, cluster-bootstrap 95% CI +14.3 to +35.7, p<0.001. The 2×2 component ablation found a +10.3-instance planning×memory interaction (F(1,8)=10.92, p=0.011), materially above the additive expectation from isolated components.

Mechanism evidence. PMCoder halved failed-action recurrence, cut give-up/empty-patch and context-exhaustion rates, and increased revert-then-refix recoveries. It still gained +12 cases (+3.8pp) on instances where no reproduction gate could fire, suggesting the planner-memory substrate contributes independently of grounding; the armed stratum gained +19 (+10.3pp).

Generality. Single-run checks were positive for DeepSeek-V4-Flash (+16), Claude Haiku 4.5 (+14), an OpenHands port (+23), and TerminalWorld (7/20 vs 5/20). These broaden plausibility but are not repeated external validation.

Section condensation

Abstract

The paper frames repository-level issue repair as a long-horizon state-management problem: an agent must retain useful observations across exploration, hypothesis, implementation, and verification while revising its strategy when work stalls. PMCoder couples a hierarchical phase planner with episodic memory so plan state conditions retrieval and memory-derived trajectory statistics can trigger replanning; issue-reproduction verdicts can additionally ground verification state in execution evidence.

The headline claim is a mean gain of 25 resolved SWE-bench Verified cases over a harness-matched Qwen baseline (+5.0 percentage points). The abstract also reports positive direction across Claude Haiku 4.5, DeepSeek-V4-Flash, an OpenHands port, and TerminalWorld, and attributes gains to the coupled design through ablation and trajectory analyses.

I. Introduction

The introduction argues that planning and memory are usually improved as separate modules even though long repair episodes make them interdependent: plans determine what historical evidence is relevant, while accumulated outcomes should determine whether the plan continues or changes. The authors position PMCoder as a two-way state system rather than a stronger base model.

The primary Qwen comparison is repeated three times because FP8 serving is not bit-reproducible. Reported means are 167.3/500 resolved for PMCoder versus 142.3/500 for baseline, with a cluster-bootstrap 95% CI for the gain of +14.3 to +35.7 and p<0.001. The introduction also reports a +10.3-instance planning×memory interaction from the 2×2 ablation and provides a Zenodo replication-package DOI.

II. Background

The background separates output-level correctness from trajectory-level state. SWE-bench grades only the submitted patch, but internal plan state determines what the model sees, when it stops, and which patch it submits. A flat transcript is both context-limited and difficult to navigate, motivating explicit phase/sub-task state plus episodic memory.

The success-signal subsection argues that return codes, self-written tests, and free-text claims of verification are weak control signals. A small motivating audit of nine pilot trajectories found narrative success prints and always-pass self-written tests; the authors explicitly state that this is not a prevalence estimate. This motivates execution-grounded updates to internal verification state.

III. Methodology — Overview and Planner

PMCoder preserves the normal repository observe-act loop and adds two coupled state structures. The deterministic planner tracks four ordered phases—exploration, hypothesis, implementation, verification—plus backtrack. One LLM call at episode start creates typed sub-tasks; per-step phase detection, bookkeeping, backtracking, and replanning are rule-based. Hysteresis dampens noisy backward/lateral phase moves.

Stuck detection can use persistent nonzero returns, repeated edits to one file, read saturation without edits, or repeated normalized actions. A backtrack marks the active sub-task failed and pushes bounded recovery work, including revert-then-refix. Terminal verification completes only when the execution-grounded completion predicate succeeds. The exported planner signal contains phase, active sub-task, progress, most-touched files, token budget, and a backtrack flag.

III. Methodology — Episodic Memory and Retrieval

Every message is mirrored into an episodic node with structured metadata; for observations, edit/file-touch metadata comes from the executed command rather than the model’s claim. Injected context is not re-ingested into memory. Retrieval preserves a fixed core and uses a token-budgeted MMR beam search; relevance fuses IDF-weighted lexical match with proximity in an incrementally built code-structure graph.

The current plan phase changes retrieval behavior: exploration/backtracking use broader diversity-oriented budgets, while implementation uses a smaller graph-weighted budget around the edit site. This phase-conditioned policy plus active-sub-task keywords implement the plan→memory direction of coupling.

III. Methodology — Injection, Grounding, and Co-Design

To preserve the tool-call/tool-result sequence, PMCoder does not rewrite history. It appends a marker-delimited plan-memory block to the most recent tool result, injecting only when plan state changes and using a novelty filter to avoid repeatedly surfacing the same nodes.

For validated issue-reproduction scripts, the system reruns the reproducer after file-mutating edits. Pass/fail is advisory text and also updates internal verification state; a verification sub-task cannot complete while the issue still reproduces. Python compile checks flag corrupted edits, and recovery can restore files to a clean committed state before refixing. The authors summarize four boundary crossings: phase→retrieval, sub-task→retrieval, memory statistics→plan, and verdict→plan.

IV. Experimental Setup

The primary benchmark is all 500 SWE-bench Verified instances, graded by the official Docker harness. Baseline and PMCoder share model, harness, tools, step budget, and grading; baseline disables planner, episodic memory, injection, and grounding. The headline Qwen and RQ4 cells use three runs. RQ3 adds single-run DeepSeek-V4-Flash, Claude Haiku 4.5, OpenHands, and TerminalWorld checks.

Runtime controls include temperature 0.0, 65,536-token vLLM context, 250 assistant turns, $3 cost cap, 60-second shell timeout, and fixed PMCoder hyperparameters selected from pilots. Reproduction scripts are generated from issue text alone without gold patch/hidden tests and admitted only if they reproduce the unmodified failure. Statistical analysis uses an instance-level cluster bootstrap plus paired McNemar tests for RQ1 and a run-level balanced 2×2 factorial model for RQ4.

V.A RQ1 — Effectiveness

Across three Qwen runs, baseline resolved 139/144/144 cases and PMCoder 170/164/168. Mean performance was 142.3 (28.5%) versus 167.3 (33.5%), a +25.0-instance / +5.0pp gain. The cluster bootstrap 95% CI was +14.3 to +35.7 with p<0.001; all three paired McNemar tests were significant (p 0.002–0.033).

The first-seed difficulty split placed most gains in the <1-hour human-fix-time tiers: +12 cases in <15 min and +17 in 15 min–1 h. In the 45 harder >1-hour instances, baseline solved none and PMCoder only two, which the authors interpret as a base-model capability ceiling rather than a state-management problem.

V.B RQ2 — Mechanism

Trajectory signatures moved in the predicted direction: failed-action recurrence fell from 0.0137 to 0.0069, give-up/empty-patch rate from 8.3% to 2.7%, context exhaustion from 6.7% to 3.0%, and mean revert-then-refix recoveries increased from 2.89 to 4.23. The post-edit reproduction verdict passed in 18/20 ultimately resolved trajectories versus 5/18 unresolved trajectories in the validated subset.

The first-seed armed/unarmed split is important for mechanism attribution. PMCoder gained +12/315 cases (+3.8pp) where no reproducer was available, showing benefit from the plan-memory substrate without the gate; with a validated reproducer it gained +19/185 (+10.3pp). The django-13516 trace provides a qualitative example in which both agents find the root cause but only PMCoder later resurfaces it after recovery.

V.C RQ3 — Generality

Single-run cross-model checks remained positive: DeepSeek-V4-Flash improved from 341/500 to 357/500 (+16, +3.2pp), and Claude Haiku 4.5 from 313/500 to 327/500 (+14, +2.8pp). An OpenHands port with Qwen improved from 146/500 to 169/500 (+23, +4.6pp).

On TerminalWorld’s official 20-task sample, PMCoder solved 7/20 versus 5/20 for baseline. These results broaden the surface beyond one model and one harness, but the paper itself correctly treats them as supporting probes rather than repeated confirmatory evaluations.

V.D RQ4 — Component Ablation

Three-run means were 142.33 baseline, 148.67 plan-only, 150.67 memory-only, and 167.33 plan+memory. The full system’s +25.0-instance gain exceeded the +14.7 expected by adding the isolated unrounded component gains.

The planning×memory interaction contrast was +10.3 resolved instances (+2.1pp), with F(1,8)=10.92 and p=0.011. This is the paper’s strongest direct evidence that the integrated system behaves as more than two independent add-ons under the fixed harness/model/budget.

VI. Discussion

The discussion interprets the effect as state management rather than new reasoning capability: PMCoder helps preserve or recover a reachable fix over long episodes, while the hard tail remains largely unsolved. Execution grounding is presented as a reliability layer for the shared state, not the benchmark oracle.

Operational overhead is limited by design: one decomposition LLM call per episode, deterministic per-step planner logic, lexical/graph memory retrieval without model calls, and at most four cached reproduction checks. For deployment, the paper suggests that issue steps or failing CI could replace the offline reproducer table when suitable.

VII. Threats to Validity

Internal validity: Qwen3-Coder both generates reproduction scripts and runs the headline agent; residual script errors can affect grounding-specific mechanism analyses. Qwen headline and ablation cells are repeated three times, but cross-model/framework/benchmark probes are single-run. Hyperparameters were fixed from pilots before final evaluation.

Construct validity: official SWE-bench resolution is a test-based proxy and can diverge from maintainer intent. RQ4 does not isolate execution grounding and edit-integrity recovery separately. External validity: the primary evidence is Verified-500 with one open-weight 30B model, and transfer to other languages/private codebases is untested.

VIII. Related Work

The paper positions existing software agents along control structure, explicit memory, execution-evidence target, and plan-memory link. The authors distinguish planning-centric systems, memory-centric experience systems, and one-directional plan→memory designs from PMCoder’s claimed two-way coupling.

For program repair, execution oracles traditionally judge finished patches or select candidates. PMCoder’s differentiating move is to apply behavioral evidence earlier, updating internal plan state during the episode. This comparative positioning is useful conceptually, but it is source-authored framing rather than an independently verified systematic review.

IX. Conclusion

The authors conclude that state loss is a consequential failure mode in long repository-level repair and that planning and memory should be designed as a coupled state system. The plan determines what memory retrieves, memory-derived signals determine when to replan, and execution evidence is used to keep verification-related state from advancing on self-report alone.

Algorithm / workflow — MMR retrieval

Inputs: task statement, recent tail, active-sub-task anchor, episodic memory nodes, phase-specific token budget.
Selection: fixed core retained; beam search adds nodes by marginal gain g(v)=λ·rel(v)−(1−λ)·max sim(v,u).
Relevance: rel(v)=wc·lex(v)+wg·graph(v), with IDF lexical match plus code-graph proximity.
Phase control: exploration/backtrack retrieve broadly; implementation retrieves narrowly around edit-site structure.
Output: budgeted working set appended with plan state to latest tool result.
Failure controls: node cap, novelty filter, no re-ingestion of injected context.

Evaluation workflow — 2×2 interaction

Cells: baseline, plan-only, memory-only, plan+memory; 3 runs per cell.
Outcome: resolved count on the fixed 500-instance benchmark.
Interaction contrast: Y11 − Y10 − Y01 + Y00 = +10.3 resolved instances (+2.1pp).
Test: run-level balanced factorial model, F(1,8)=10.92, p=0.011.
Interpretation: full coupling exceeds the additive expectation from isolated component gains.

Implementation / practice takeaways

1. Keep control state typed and external.
Represent phase, active sub-task, progress, edit churn, and recovery state explicitly instead of expecting the base model to reconstruct them from transcript history.
2. Make retrieval conditional on current work.
Use phase/sub-task to control memory budget and ranking so old evidence is resurfaced when relevant rather than by recency alone.
3. Feed memory back into planning.
Edit counts, repeated actions, and saturation signals should be allowed to force plan revision; otherwise “memory” remains passive context.
4. Ground progress, not just final output.
Execution evidence can update internal completion/recovery state without becoming the official grader or blocking the agent’s action policy.
5. Preserve tool-call distribution.
Appending state to a tool result is a practical alternative to rewriting message history when tool-call/tool-result pairing matters.
6. Test coupling, not components only.
A factorial design or equivalent interaction test is more informative than comparing full system against baseline and isolated modules independently.
Do not overclaim. The study does not show that planning+memory solves hard repairs beyond base-model capability, that a reproduction script is always available or correct, or that the design generalizes to private/multilingual codebases or production software-maintenance workflows.
