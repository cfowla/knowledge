One-page synthesis

Verdict: Read first. The paper is unusually useful as an evaluation-methods warning for stateful agents: it shows that self-improvement claims can be swamped by ordinary run variance, depend on benchmark task order, and encode wrong lessons when task/environment feedback is underspecified.

The empirical re-evaluation upgrades the model/harness baseline, repeats whole task streams three times, and adds two shuffled task orders. The central reliability result is not merely that scores move: adding memory raises run variance in 17/24 domain-method comparisons, and changing task order often flips small default-order gains into degradation. On WebArena the strong no-memory baseline is 54.8, AWM is 54.1, and ReasoningBank is 56.3 under the default order; under shuffled orders both memory methods can fall below baseline. The abstract summarizes ReasoningBank as +1.5 points under default order versus −4.5 under shuffled order.

The failure analysis is operationally valuable. The memory builder may write advice that is plausible but impossible in the environment, overreact to ambiguous tasks, learn from evaluator false negatives, or preserve a rewarded but unintended workaround. Adding rubric details, environment action feedback, and explicit prompt constraints improves shuffled-order performance, but the authors report that this recovers only 31% of the degradation. The residual 69% gap prevents a strong causal claim that underspecification alone explains fragility.

Section condensation

1 Introduction

The paper frames self-improving agents as stateful systems whose early errors can alter later behavior. It re-evaluates AWM and ReasoningBank on three web benchmarks with a stronger initialization, repeated runs, and randomized task order.

The headline concerns are large run-to-run spread and hidden dependence on task sequence. The authors then inspect memory contents to identify task and environment underspecification as candidate mechanisms and test targeted specification inputs.

2 Background: Memory-Based Self-Improving Agents

An agent processes an online task stream while maintaining textual memory. After each task, a construction module updates memory from the trajectory and reward; later tasks consume all AWM workflows or retrieved ReasoningBank items.

AWM emphasizes reusable stepwise workflows from successes. ReasoningBank writes broader reasoning insights from successes and failures and retrieves selected memories, creating more flexible but also potentially more contaminable state.

3.1 Experiment Setting

Benchmarks are WebArena (812 tasks), VisualWebArena (910), and SCUBA (267 retained after invalid-task exclusions). The authors use contemporary baseline harnesses and typically GPT-5-mini for both acting and memory construction.

Each key setting is run three times. Reporting includes average pass@1, standard deviation across runs, and best–worst gap. Two shuffled orders are added to the default order. Ground-truth reward is used during memory construction to avoid adding LLM-judge noise to the diagnostic experiments.

3.2 Variance

Even the no-memory agent is noisy: domain-level best–worst gaps reach several percentage points. Memory can amplify the spread because the state at task t depends on previous stochastic outcomes and generated memories.

Across Table 1, variance rises in 17/24 comparisons and rises by more than 50% in 11. Stronger baseline capability also shrinks apparent self-improvement gains: ReasoningBank’s +1.5-point WebArena gain over baseline has p=0.23 across three runs.

3.3 Task Order

The default task sequence embeds difficulty structure rather than a neutral random stream. In two WebArena domains, later task IDs are substantially harder, creating an implicit curriculum that can advantage methods that learn online.

Shuffling reverses the story in many cases: significant degradation appears in 6/8 displayed shuffled-order comparisons. This matters because a deployment cannot assume a curated easy-to-hard stream of user requests.

4.1 Failure Modes in Memory Construction

Manual inspection finds environment mismatch, task ambiguity, evaluator artifacts, and propagation of unintended workarounds. The memory generator can recommend APIs in a browser-only environment, request unavailable user confirmation, or write irrelevant lessons after misinterpreting a task.

Because memory is stateful, a questionable lesson can become self-reinforcing. The Haversine example shows a rewarded fallback entering memory at different times across runs and then being repeatedly retrieved, offering a plausible mechanism for variance amplification.

4.2 Addressing Underspecification

The authors add three information channels to ReasoningBank memory construction: evaluator rubrics/scores, environment execution feedback, and an explicit prompt that favors executable web-navigation procedures while rejecting unsupported strategies.

Each ablation provides a modest Shuffle-1 gain; the combined setting improves 49.8→52.7 and improves Shuffle-2 50.7→51.8 without reducing the default-order score. The agent still trails the no-memory baseline under both shuffled orders, so the intervention is partial rather than corrective.

5 Related Works + 6 Conclusion

The paper positions its contribution at the intersection of agent continual learning, memory/skills, and reliability science. Its main methodological claim is that reliability must be measured across the evolving task stream, not inferred from a single run.

The authors recommend multiple runs, randomized task orders, well-specified pilots followed by underspecified stress tests, memory validation, iterative specification, and human oversight. They report 31% recovery of the observed degradation, leaving 69% unexplained.

Appendices

Appendix A limits the claim to two memory methods and web browsing and notes that memory review was qualitative and incomplete. Appendix B provides cost and licensing details. Appendix D reports baseline pass@3/pass^3 metrics, Appendix E exposes the original prompts, and Appendix F gives concrete failure cases.

The appendices materially strengthen interpretability and reproducibility, especially by showing how generic memory prompts and evaluator artifacts can produce wrong lessons. The NeurIPS checklist is administrative and is not treated as independent evidence.

Figure 1 — Memory-based self-improving workflow

Tasks are processed sequentially. After each task, AWM or ReasoningBank writes textual memory; later tasks retrieve or receive stored memory. AWM stores reusable workflows from successful trajectories; ReasoningBank stores broader insights from successes and failures and retrieves relevant items.

Table 1 — Variance across three runs

Across 24 domain × memory-method comparisons, 17 show higher cross-run standard deviation after adding memory, and 11 exceed a 50% relative increase. GitLab best–worst gap rises from 4.44 points at baseline to 7.78 with ReasoningBank; the largest shown gap is 10.42 points in WebArena Multisite with ReasoningBank.

Table 2 — Stronger initialization context

The authors’ GPT-5-mini no-memory baseline reaches 54.8 on all 812 WebArena tasks and 55.3 on the 684-task subset used for the prior ReasoningBank comparison, matching or exceeding older memory-enhanced results.

Table 3 — Overall benchmark performance

Average pass@1 across three runs: WebArena 54.8 baseline / 54.1 AWM / 56.3 ReasoningBank; VisualWebArena 54.9 / 54.5 / 55.6; SCUBA 49.6 / 50.1 / 51.1. Gains over a stronger baseline are small and inconsistent.

Figure 2 — Implicit curriculum

Moving-average pass rate varies systematically with default task position. WebArena Shopping Admin and GitLab become harder later in the sequence; VisualWebArena Shopping is nonuniform and oscillatory. The default order therefore carries task-difficulty structure.

Figure 3 — Task-order sensitivity

Shuffling task order causes significant degradation in 6 of 8 displayed cases. On WebArena, default scores are 54.1 AWM and 56.3 ReasoningBank versus 49.1/49.8 for Shuffle-1 and 49.8/50.7 for Shuffle-2, against a 54.8 baseline.

Figure 4 — Memory contamination traces

Unsupported API suggestions and Haversine routing fallbacks appear at different points across runs and accumulate in retrieved memory. The timing is stochastic, and earlier appearance yields more later retrieval opportunities.

Table 4 — Specification inputs

The mitigation adds three information channels during memory construction: function-based rubrics/scores, environment execution errors, and a prompt that explicitly favors procedural web-navigation knowledge while rejecting unsupported strategies.

Figure 5 — Mitigation ablation

Under Shuffle-1, original ReasoningBank is 49.8; rubric feedback 52.3; environment feedback 50.9; prompt modification 50.9; all three 52.7. The combined intervention also improves Shuffle-2 from 50.7 to 51.8 while preserving the default-order score.

Appendix Tables 5–6 — Baseline robustness metrics

The appendix reports average pass, pass@3, and pass^3 for the no-memory baseline. This helps distinguish task-level capability variability from whole-sequence self-improvement variability.

Appendix Listings 1–3 — Memory prompts

AWM encodes short reusable workflows. ReasoningBank asks for up to three generalizable memory items from successful or failed trajectories. The prompts emphasize generalization but do not, in the original form, fully specify environment constraints or evaluator intent.

Appendix Tables 7–9 — Failure cases

Three concrete cases show: an ambiguous shopping task interpreted as medical question answering; a correct $0.00 answer failing a strict string rubric and producing an irrelevant lesson; and a rewarded Haversine fallback that becomes a reusable but unintended routing strategy.

Evaluation and appraisal

Best use: evaluation-design controls for stateful agents, memory-governance requirements, and a warning against single-run self-improvement claims.

Do not use for: assuming that all agent memory is harmful, that task order explains all fragility, or that the reported effect sizes generalize beyond these web benchmarks and two memory methods.

Rationale: Directly addresses reliability controls for stateful/self-improving agents.

Evidence: Repeated-run, task-order, memory-audit, and feedback experiments.

Limiting factor: Domain is limited to web browsing and textual memory.

Would raise/lower: Replication across coding/research/clinical agent tasks.

Evidence: Default versus shuffled order, variance decomposition, memory failure examples.

Limiting factor: The ingredients—variance, curriculum effects, underspecification—are individually established ideas.

Would raise/lower: Broader causal characterization of the remaining failure sources.

Evidence: Three runs per setting, two shuffled orders, no-memory comparisons, ground-truth rewards for diagnosis.

Limiting factor: Causal attribution to underspecification remains partial and 69% of the gap is unresolved.

Evidence: WebArena, VisualWebArena, and enterprise-oriented SCUBA provide some environment diversity.

Limiting factor: No coding, research, embodied, clinical, or newer memory-management systems.

Would raise/lower: Cross-domain and cross-architecture replications.

Implementation value 9/10

Rationale: Provides concrete evaluation and memory-governance controls that can be adopted immediately.

Evidence: Repeated runs, shuffled orders, rubric detail, environment feedback, explicit constraints, memory validation, human oversight.

Limiting factor: Exact effect sizes and the optimal run count are not established outside this setup.

Would raise/lower: A reusable benchmark harness with automated memory-validity checks and uncertainty reporting.

Strengths

  • Directly re-tests published memory methods rather than proposing a new method and evaluating only its best case.
  • Separates baseline agent noise from additional stateful-learning variance.
  • Uses stronger contemporary baselines, multiple complete runs, and alternate task orders.
  • Links aggregate reliability failures to inspectable memory traces and then tests targeted interventions.
  • Provides code/data links and exposes key prompts and failure cases in the appendix.

Limitations and interpretation

  • Three runs are enough to reveal large instability but are a thin basis for precise variance or significance estimates.
  • The unpaired t-test over three runs is weak inferential support; the paper’s main value is the magnitude and direction of instability, not a definitive p-value.
  • The manual memory audit is qualitative and partial, so underspecification is a plausible contributor rather than a complete causal explanation.
  • Only AWM and ReasoningBank are tested, both in web browsing; newer memory managers and other stateful learning mechanisms may behave differently.
  • Some benchmark artifacts are themselves part of the failure mechanism, which is important operationally but complicates claims about intrinsic agent behavior.

Implementation and evaluation takeaways

Evaluation harness

Make repeated whole-sequence runs and randomized task orders first-class controls. Report mean, standard deviation, and best–worst gap rather than one score.

Benchmark hygiene

Measure difficulty versus task position and inspect evaluator false negatives. In a learning loop, a scoring bug can become a training-data bug.

Memory contract

Store environment constraints, execution feedback, and task/rubric context with the memory-writing step. Do not let plausible text become trusted state merely because it was generated after a rewarded trajectory.

Validation boundary

Before a memory is reusable, test it for environment executability, task relevance, evaluator correctness, duplication, and conflicts with higher-authority constraints.

Human oversight

Expose an inspect/reject/correct path for persistent memories, especially when subsequent actions are costly or irreversible.

What remains open

The tested specification inputs recover only part of the degradation. A robust system still needs causal diagnosis of the unexplained gap and cross-domain replication.
