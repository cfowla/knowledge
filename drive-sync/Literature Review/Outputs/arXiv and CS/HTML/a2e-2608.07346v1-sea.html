One-page synthesis

Core thesis. Agent harnesses materially shape deployed agent behavior beyond the underlying model. A2E therefore evaluates the complete harness–model system by decoupling tasks from harnesses through ATP, instrumenting native execution with span-based tracing, and assessing reasoning, action, answer, and runtime quality rather than final correctness alone.

Architecture. A2E has three principal layers. The Task Layer uses the Agent Task Protocol (ATP) to separate benchmark adaptation from harness execution. The Monitor Layer maps heterogeneous agent-runtime activity into a common semantic/span representation built on OpenTelemetry/OpenInference concepts. The Evaluation Layer registers metrics by lifecycle stage and dimension, combines deterministic and LLM-as-judge evaluation, and stores traces/results/metrics centrally so new metrics can be applied later without rerunning the agent.

Main empirical finding. Harness choice matters most where the task requires multi-turn execution, tool use, and longer-horizon control. In the 23-benchmark correctness matrix, some single-turn tasks produce identical outcomes across all nine harnesses, while τ-bench spans 0.00–0.60, GDPVal 0.00–0.60, and Traject-Bench 0.20–1.00. Average correctness across all 23 benchmarks ranges only 0.57–0.68, but process and efficiency signals separate harnesses more strongly.

Efficiency finding. Across the 855 non-sandbox runs, mean correctness among the eight harnesses with token telemetry spans about 0.568–0.663 while mean token consumption spans 2,063–7,319 tokens per run. The paper highlights Smolagents as using 3.5× the tokens and 2.4× the turns of Claude-Agent-SDK for only 1.04× the correctness. Agno has the highest mean correctness in this analysis (0.663) while also being the second-cheapest by recorded tokens.

Cross-benchmark finding. Under GLM-5.2, the success–efficiency frontier changes by benchmark: the paper ranks CrewAI first on GDPVal, OpenAI Agents first on MMLU-Pro, and LangGraph first on τ³-bench using a normalized distance-to-“sweet spot” score. The point is not that these rankings are stable, but that the same base model can yield different operational behavior when wrapped by different harnesses.

Important internal inconsistency. Table 2 labels the LangGraph trajectory as successful and describes the correct account-level diagnosis, yet prints correctness=0.0. Section 6.3 immediately states that the same LangGraph trajectory obtains correctness=1.0. The table also prints task_succeeded=1.0 for the CrewAI trajectory despite describing it as failed. These values should not be silently reconciled.

Section-by-section condensation

Abstract

The paper frames agent harnesses as critical deployment infrastructure whose prompts, tools, context policies, and execution loops can materially alter system behavior. A2E is proposed as an end-to-end harness evaluation engine built around three linked capabilities: ATP for benchmark–harness composition, automatically instrumented execution traces, and multidimensional evaluation spanning planning, tool use, task completion, safety, and runtime efficiency.

The authors claim that harness–model combinations vary substantially by task and that no single combination dominates. Figure 1 previews this argument: correctness varies relatively narrowly across harnesses while planning, tool-use, safety/operational, and efficiency metrics show wider ranges.

1. Introduction

The motivation is a gap between benchmark orchestration and native agent observability. Systems such as Inspect AI are described as strong benchmark runners but requiring harness-specific integration paths, whereas OpenInference/Phoenix-style systems standardize tracing but do not by themselves provide complete benchmark orchestration and result verification. A2E seeks a lighter substrate that preserves native execution while unifying evaluation.

The proposed system has a Task Layer, Monitor Layer, and Evaluation Layer, with persistent database storage rather than standalone logs. The introduction previews two empirical claims: model–harness effectiveness is task-dependent, and endpoint correctness has limited resolution compared with process/operational metrics.

2. Overview · 2.1 Framework · 2.2 Pipeline

The Task Layer organizes benchmarks by time, category, and difficulty and packages execution resources into a bundle containing sandbox definition, task dataset, experiment configuration, and runtime environment. The Monitor Layer normalizes access to representative and SDK-based agents, attaches a common monitor, and records model calls, state transitions, errors, tools, latency, tokens, and artifacts as ordered trajectories. The Evaluation Layer combines rule-based metrics with LLM-as-judge metrics and stores trajectory, result, and metric records centrally.

The runtime pipeline is intentionally separated into Task, Server, Evaluation, and UI components. The task runner writes runs/traces to the server; evaluators pull traces and outcomes, compute metrics, and write results back; the UI is read-only. This is a strong architectural choice for reproducibility because visualization cannot mutate experiment state.

3. Monitor Layer · 3.1 Instrumentation · 3.2 Span-Based Traces

Instrumentation is divided into semantic, span, and SDK layers. The semantic layer names principal agent behaviors (agent, chain, model call, tool, skill); the span layer records bounded operations with timing, status, context, and parent–child links; the SDK layer translates framework-specific calls and transitions into that common representation. This isolates framework adapters from the higher-level trace schema.

OpenTelemetry-style spans preserve both chronology and causal hierarchy. A top-level agent span can contain reasoning chains, model calls, tools, and skills, allowing evaluation to locate latency, failures, diverging execution paths, and external capability use rather than relying on final responses alone.

4. Task Layer · 4.1 ATP · 4.2 Harnesses & Benchmarks · 4.3 Trajectory Generation

ATP is explicitly an internal software protocol, not a network protocol. Four objects define the boundary: TaskInput stores instruction/state/expected actions/outputs/metadata/sandbox; AgentBinding supplies tools and prompt construction; AgentRunner executes a harness; and TaskTrace normalizes status, answer, and ordered tool calls. Benchmark adapters create task/binding objects while harness adapters keep model clients, control loops, tool conversion, and output normalization inside the harness.

The registry covers Agno, AutoGen AgentChat, CrewAI, Google ADK, LangGraph, LlamaIndex, OpenAI Agents SDK, Smolagents, and Anthropic/Claude Agent SDK. Twenty-three benchmarks are grouped into coding, conversational, research, and computer-use areas, with text, tool-use, and sandbox dataset adapters. A run records harness/model/SDK/dataset key, sample seed, and task IDs; reproducibility additionally requires the same dataset version, endpoint, and run settings.

5. Evaluation Layer · 5.1 Lifecycle-Aligned · 5.2 Extensible · 5.3 Scalable

The evaluation taxonomy separates four lifecycle stages: Reasoning (Task, Flow, Logical), Action (Tool, Skill, Memory), Final Answer (Answer Correctness, Task Completion), and Runtime Quality (Efficiency, Safety). The paper positions this as an organizational interface rather than a fixed checklist: a metric is registered by stage/dimension while its implementation may be an LLM judge, deterministic rule, environment verifier, or statistical aggregation.

Evaluation runs over structured database records containing task, configuration, turns, model outputs, tool calls, status, errors, and resource use. The design supports incremental evaluation: once a trajectory is stored, new metric versions or judge models can rescore it without rerunning expensive agent execution. Large artifacts may remain external while identifiers are indexed in the database.

6.1 Harness–Benchmark Evaluation Matrix

Nine harnesses share the same DeepSeek-V4-pro (FP4) backbone, inference settings, tool setup, step limit, and timeout. Each of 23 benchmarks contributes five aligned tasks, producing 1,035 scored runs. Nineteen non-sandbox benchmarks contribute 855 fully traced runs and 19,665 metric records. Because only five tasks populate each cell, correctness moves in 0.20 increments and per-cell variance is necessarily high.

Single-turn tasks such as ARC-Challenge, GSM8K, OpenBookQA, and HumanEval often show little or no harness separation, while multi-turn tasks show larger spreads. The full 23-benchmark average is highest for Agno (0.68), followed by LlamaIndex (0.64) and Smolagents (0.63), but the authors explicitly state that the table is not intended as a framework ranking. Over only the 19 non-sandbox benchmarks, LlamaIndex would lead 0.77 vs 0.74 for Agno.

6.2 Cross-Benchmark Harness Comparison

A second experiment fixes GLM-5.2 as the API model and compares nine harnesses on GDPVal, MMLU-Pro, and τ³-bench. Success is plotted against average completion tokens, and the authors compute a normalized distance-to-ideal score. The top-ranked harness changes by benchmark: CrewAI on GDPVal, OpenAI Agents on MMLU-Pro, and LangGraph on τ³-bench.

The intended inference is architectural rather than ordinal: prompt construction, tool representation, context management, control loops, error handling, and termination policies can change both success and cost even when the underlying model is fixed. Longer-horizon/tool-interactive τ³-bench shows the strongest separation.

6.3 Case Study

The case study compares LangGraph and CrewAI on the same τ³-bench task with GLM-5.2. LangGraph reaches the account-level diagnosis using 3 turns, 4 LLM calls, 3 tool calls, and 10,122 tokens; CrewAI continues device-level troubleshooting for 5 turns, 9 LLM calls, 5 tool calls, and 96,704 tokens. Prompt tokens are 8,520 vs 94,615 and reported cost is 0.0051 vs 0.0430.

The narrative reports LangGraph correctness 1.0 and CrewAI correctness 0.0, making the example a useful demonstration of trajectory diagnosis: the failure can be localized to context accumulation, tool selection, missing goal-relevant action, and termination. However, Table 2 prints contradictory metric values for the successful LangGraph trajectory and should be treated as a source-level reporting defect.

Evaluation and appraisal

Verdict: Read first. Best for readers designing agent-evaluation infrastructure, trace/provenance systems, or harness-comparison studies. Its strongest contribution is architectural integration rather than a definitive empirical ranking of agent frameworks.

Relevance

9.0/10

Rationale: Highly relevant to agent evaluation, harness auditing, trajectory observability, and reliability engineering.

Evidence basis: The paper directly addresses harness-level evaluation and process-aware metrics across multiple agent frameworks.

Principal limiting factor: Relevance depends on whether the reader builds or evaluates agent systems; it is less useful for model-only evaluation.

Would raise/lower score: Broader evidence connecting the framework to production incident detection or governance would increase practical relevance.

Novelty

8.0/10

Rationale: The contribution is strongest in end-to-end integration: ATP + minimally invasive tracing + lifecycle-aligned evaluation + persistent re-evaluation.

Evidence basis: The architecture unifies concerns commonly split across benchmark runners and observability systems.

Principal limiting factor: Several building blocks—OpenTelemetry, benchmark adapters, LLM-as-judge, metric registries—are established ideas.

Would raise/lower score: Direct comparative engineering analysis against existing end-to-end frameworks would clarify the incremental contribution.

Method strength

6.5/10

Rationale: The matched harness comparisons are controlled at the task and model level, but the empirical design is thin per cell.

Evidence basis: Nine harnesses × 23 benchmarks × five aligned tasks yields 1,035 scored runs; 855 non-sandbox runs receive trajectory analysis.

Principal limiting factor: Five tasks per cell gives a 0.20 score resolution; there is no uncertainty analysis, repeated seeds, or statistical test of harness differences.

Would raise/lower score: More tasks, repeated seeds, confidence intervals, sensitivity analyses, and explicit version pinning would strengthen the design.

Evidence strength

6.0/10

Rationale: The experiments demonstrate that A2E can execute and expose meaningful harness differences, but they do not establish stable rankings or validate every metric.

Evidence basis: Correctness, token/turn metrics, trajectory profiles, and a same-model case study all show implementation-level variation.

Principal limiting factor: No formal uncertainty reporting; some trajectory metrics are instrumentation-derived; the case-study table contains an internal correctness inconsistency.

Would raise/lower score: Independent replication, judge-metric validation, uncertainty estimates, and resolution of reporting inconsistencies would raise confidence.

External validity

5.5/10

Rationale: Benchmark breadth is substantial, but transfer to production deployments and future harness versions is uncertain.

Evidence basis: The evaluation spans 23 benchmarks, four task areas, nine harnesses, sandbox and non-sandbox tasks, and two model backends across experiments.

Principal limiting factor: Benchmarks are sampled sparsely; harnesses evolve quickly; model coverage is limited; deployment conditions are not evaluated.

Would raise/lower score: Multi-version longitudinal runs, more models, production-like environments, and independent sites would improve generalizability.

Implementation value

8.5/10

Rationale: The architectural patterns are concrete and directly reusable for agent-evaluation infrastructure.

Evidence basis: ATP boundaries, span-based native tracing, database-backed metric versioning, and read-only visualization are described clearly.

Principal limiting factor: The paper does not fully specify all metric implementations, judge prompts, versioning policy, or operational hardening details.

Would raise/lower score: Complete reproducibility manifests, metric definitions/prompts, schema/version policies, and failure-recovery tests would make it more build-ready.

Main strengths

  • Correct evaluation unit: treats the deployed harness–model system, not just the foundation model, as the object being evaluated.
  • Clean boundaries: ATP separates benchmark logic from harness logic; monitor adapters separate framework-specific tracing from the common semantic/span model.
  • Native-execution orientation: observability is attached to the harness rather than forcing execution through a proxy that could change behavior.
  • Process-aware evaluation: correctness is supplemented with planning, tool, completion, resource, and safety dimensions.
  • Persistent re-evaluation: storing trajectories separately from metric computation supports metric versioning and longitudinal auditing.
  • Aligned comparisons: the main 23-benchmark matrix uses identical task IDs per harness under a fixed base model/configuration.

Main limitations

  • Sparse per-cell sampling: five tasks per harness–benchmark pair makes 0.20 the minimum correctness increment and prevents stable per-benchmark ranking.
  • No uncertainty analysis: no confidence intervals, repeated seeds, formal variance analysis, or hypothesis tests accompany the main comparisons.
  • Metric validity is incompletely established: the architecture organizes many metrics, but the paper does not independently validate every LLM-judge or process metric as a reliable measurement construct.
  • Instrumentation confounding: Figure 6 explicitly marks some rows as instrumentation-set rather than agent behavior.
  • Model scope: the main matrix uses DeepSeek-V4-pro; the three-benchmark/case-study analyses use GLM-5.2. This demonstrates the framework, but does not show robustness across a broad model panel.
  • Rapidly changing harness ecosystem: results are sensitive to framework versions, default prompts, tool adapters, and control-loop policies; registry support itself does not guarantee every pair has passed full validation.
  • Internal reporting inconsistency: Table 2 conflicts with Section 6.3 on the successful LangGraph correctness value and prints task_succeeded=1.0 for the failed CrewAI trajectory.
  • Deployment gap: benchmark success and safety metrics are not equivalent to production reliability, governance, or operational safety.

What the evidence supports

Supported: harness implementation can materially change success, tool behavior, token/turn efficiency, and trajectory characteristics even under a fixed underlying model; outcome-only evaluation can miss meaningful execution differences; the A2E architecture can organize heterogeneous harnesses/benchmarks into a common evaluation workflow.

What not to overclaim

Not established: a universal best agent harness; statistically stable per-benchmark rankings; validated causal attribution of every metric difference to a specific harness design choice; deployment safety; or generalization to future harness/model versions.

Implementation takeaways

1. Evaluate the complete system

Treat model + harness + prompt policy + tool representation + control loop + termination logic as the deployed unit. Model-only scores are insufficient when the harness changes behavior.

2. Decouple task contracts from harness adapters

ATP’s strongest reusable pattern is the stable task/binding/runner/trace boundary. New benchmarks and new harnesses should plug into independent sides of the interface rather than requiring pairwise integration.

3. Instrument native execution

Prefer observational adapters that map framework-native calls into a stable semantic/span schema. Avoid evaluation plumbing that changes the invocation path when trajectory fidelity matters.

4. Store trajectories before scoring

Persist raw normalized traces and provenance independently of metric results. This permits new evaluators, judge versions, and aggregation rules to be applied without re-running expensive agents.

5. Version every evaluation dimension

The paper implies—but does not fully specify—the need to version metric definitions, judge models/prompts, harness versions, benchmark versions, seeds, model endpoints, and run settings.

6. Keep outcome and process metrics separate

Correctness, task completion, planning quality, tool behavior, and runtime cost answer different questions. Do not collapse them into a single score unless the aggregation rule and trade-offs are explicit.

7. Add uncertainty before ranking

For comparative use, increase sample sizes, repeat seeds, report confidence intervals, and test sensitivity to task composition. The paper itself warns that five-task cells are too coarse for strong rankings.

8. Treat metric provenance as first-class

Figure 6 shows why: some values may be instrumentation-derived rather than agent-derived. Every metric should carry source, computation method, version, and applicability metadata.

9. Build consistency checks into evaluation QA

The Table 2 contradiction is a concrete example of why result tables, narrative claims, and stored records should be cross-validated mechanically before publication or dashboard display.
