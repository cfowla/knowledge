One-page synthesis

Core thesis. Once a faulty persistent memory has already contaminated an agent’s claims, actions, tool use, or derived memories, deleting the root record is insufficient. The paper proposes repairing the persistent store and the dependent execution trace jointly, using explicit provenance to identify what must be deleted, quarantined, invalidated, preserved, or replayed.

The proposed method constructs a typed graph over user inputs, memory records, and execution steps. Starting from a diagnosed faulty-memory set, it traces downstream dependency edges, checks whether affected candidates have independent trusted support outside the contaminated region, applies deterministic rollback rules, and selectively replays only answer-relevant executable steps plus the dependencies needed to regenerate them. The final answer is always regenerated under the repaired state. This architecture intentionally separates fault diagnosis from repair.

On a 150-case controlled tool-use benchmark, the method reports 0.853 recovery, complete diagnosed-fault removal, complete benign-memory preservation, 0.123 replay ratio, and 5.70 LLM calls per case. Recovery is higher than the six reported baselines, but the result is not uniformly dominant: LLM-judge and AgentTrace-style have higher claim-invalidation F1 on the controlled set, and LLM-judge has lower recurrence. On the selected 50-case adapted LongMemEval-V2 stress test, recovery falls to 0.680—explicitly framed by the authors as evidence that the controlled result is an upper bound rather than a deployment estimate—while remaining higher than the compared baselines.

Section condensation

Abstract & 1. Introduction

The paper defines a post-failure recovery problem for memory-augmented agents: a faulty memory may be retrieved, cited, turned into claims, used to parameterize actions, or consolidated into new persistent memories. Repair therefore must cover both the original faulty state and its downstream consequences. The authors argue that existing memory editing or auditing approaches commonly focus on the store itself and can leave contaminated trace state intact.

The proposed contribution is dependency-guided rollback repair, combining memory-to-action provenance, independent-support checks, deterministic rollback planning, and selective replay. The paper also contributes a controlled memory-repair benchmark designed specifically to test recovery after diagnosed faults rather than detection.

2. Related Work

The related-work framing connects agent memory management and poisoning/staleness research to causal/provenance tracing, program slicing, and database rollback. The paper positions its novelty in adapting these ideas to persistent memory plus execution repair in tool-using agents, rather than claiming that provenance or rollback theory itself is new.

3.1 Problem Setting

Repair receives a user session, persistent memory store, failed execution trace, diagnosed faulty-memory set, available tools, and runtime provenance. The diagnosis is taken as given. The output is a corrected answer, repaired execution trace, and repaired active memory state.

The operational boundary is important: the method can replay tools only where execution is resettable, idempotent, or compensatable. Irreversible external side effects cannot be undone by graph reasoning alone.

3.2 Dependency Graph Construction

The graph combines user-input, memory, and typed execution-step nodes. Deterministic edges encode initiation, citation/support, memory production and mutation, supersession/derivation, and execution order. Provenance and lifecycle relations point from antecedents to dependents. Execution-chain edges retain order but are not used as contamination-propagation edges.

3.3 Fault Provenance & Affected Subgraph Tracing

Each diagnosed fault is mapped to a provenance seed when available, and the method traverses downstream propagation edges under temporal constraints to construct a raw affected set. Reachability is treated as possible contamination rather than automatic invalidation, leaving support checking to distinguish affected-but-still-justified outputs.

3.4 Independent-Support Checking

An affected candidate may be preserved only if it has admissible support from outside the diagnosed/affected region. Candidates within the contaminated region are not allowed to recursively certify one another. This creates a conservative boundary between evidence that survives rollback and evidence that must be invalidated or regenerated.

3.5 Rule-Guided Rollback Planning

The planner deterministically deletes diagnosed faulty memories, quarantines unsupported affected memories, preserves independently supported outputs, invalidates unsupported dependent trace state, and identifies steps needing replay. Answer relevance narrows replay: unsupported affected nodes that do not contribute to the final answer can be invalidated without regeneration.

3.6 Selective Replay

The executor applies memory dispositions first, processes replayable steps in original trace order, supplies preserved outputs as fixed context, withholds invalidated claims until regenerated, and reissues required tool actions rather than reusing observations whose generating action was invalidated. Valid replayed memory mutations update the repaired store.

The final answer is always regenerated. This design makes replay cost controllable, but the ablation shows an explicit durability trade-off: removing selective replay greatly expands replay and LLM use while lowering recurrence.

4. Controlled Memory-Repair Benchmark

The benchmark contains 150 multi-turn tool-use cases across shopping, travel, and customer support. Four primary fault strata are injected: poisoned, stale, wrong-user, and summary-drift. A case is retained only when the injection changes the final answer and produces at least one downstream effect; 128 cases contain one diagnosed faulty memory and 22 contain two or three.

At repair time, methods receive only the faulty state/trace and diagnosed fault identifiers; the paired clean trace, expected answer, benign-memory labels, and affected-node annotations are evaluation-only. Metrics cover immediate recovery, recurrence on recovered cases, faulty-memory removal, benign preservation, claim-invalidation F1, replay ratio, and LLM-call cost.

5. Experiments

All main controlled comparisons use GPT-4o in the same tool environment, with temperature 0 and seed 42; supplemental Gemini-3.6-Flash and Qwen3.6-27B runs assess backbone sensitivity. The paper compares no repair, three memory-centric baselines, and three trace/plan-oriented approaches including the proposed method. Results are single-run measurements rather than repeated trials with uncertainty intervals.

5.1 Main Results

The proposed method achieves the highest controlled recovery (0.853), complete diagnosed-fault removal, and complete benign-memory preservation. Compared with LLM-judge repair, reported recovery is 8.0 percentage points higher while replay ratio is 43.3% lower and LLM calls are 41.8% lower. AgentTrace-style is cheaper but recovers 0.607 and fails to remove diagnosed faulty memories in the reported setup.

Metric trade-offs matter. LLM-judge repair has lower recurrence (0.121 vs 0.266) and much higher claim-invalidation F1 (0.946 vs 0.566), while AgentTrace-style also has higher claim-F1 (0.853). The authors therefore interpret recovery, recurrence, persistent-state repair, and cost jointly rather than claiming dominance on all dimensions.

5.2 Ablation Study

Removing the rollback planner lowers recovery from 0.853 to 0.713, increases recurrence to 0.430, and raises LLM calls from 5.70 to 9.19, supporting the planner’s role in both answer recovery and limiting unnecessary repair. Removing support checking increases raw recovery to 0.880 but reduces benign preservation and increases replay/calls, indicating that support checking trades a small amount of immediate recovery for selectivity.

Removing selective replay produces the clearest efficiency trade-off: recurrence improves to 0.071, but replay ratio rises from 0.123 to 0.755 and LLM calls from 5.70 to 24.01. The full method therefore prioritizes targeted repair rather than exhaustive recomputation.

5.3 Transfer to Adapted LongMemEval-V2 Subset

The transfer test uses 50 selected externally derived procedural/navigation cases converted into the repair schema. It is poisoned-fault focused and predominantly multi-fault: 45/50 cases contain two to four diagnosed faulty memories. It is explicitly presented as an end-to-end transfer stress test, not a full fault-type coverage study.

The proposed method reaches 0.680 recovery versus 0.540 for AgentTrace-style and 0.260 for LLM-judge, and has the highest claim-invalidation F1 (0.669). AgentTrace-style retains a cost and recurrence advantage. The 17.3-point absolute recovery drop from the controlled set is treated by the authors as evidence that controlled performance should not be interpreted as a deployment estimate.

6. Conclusion

The authors conclude that dependency-guided rollback can repair both faulty persistent state and dependent execution while limiting recomputation. They identify recurrence robustness and claim-state identification as remaining gaps. The empirical evidence supports the method as a promising, implementable recovery architecture under instrumented provenance, not as a complete memory-safety solution.

Appendices A–I

The appendices are unusually important for reproducibility. They specify data schemas, graph labels, rollback-plan fields, prompt contracts, deterministic rollback rules, fault injection, metric definitions, per-domain/fault/backbone/cost/robustness results, four worked case studies, baseline implementations, and the construction/fault multiplicity of the adapted LongMemEval-V2 subset.

Evaluation & appraisal

Verdict: Read first. Best treated as a build-useful architecture and benchmark paper for provenance-aware recovery in memory-augmented agents. It is not deployment-validating evidence and should not be used to infer general memory-fault detection performance or universal LongMemEval-V2 performance.

Relevance

Rationale: Directly addresses persistent agent memory, provenance, recovery, replay, and reliability.

Evidence basis: End-to-end method plus benchmark, ablations, transfer, implementation contracts.

Principal limit: Applicable mainly to agents with detailed runtime provenance and controllable tool side effects.

Would change score: Lower if provenance cannot be instrumented; higher only with demonstrated production integration across heterogeneous agent stacks.

Rationale: The useful novelty is the joint adaptation of dependency tracing, support preservation, deterministic rollback planning, and selective replay to memory-to-action agent state.

Evidence basis: Explicit typed graph, state/trace dispositions, executor, and new repair benchmark.

Principal limit: Provenance, program slicing, and rollback are established ideas; the paper appropriately frames the contribution as adaptation/integration.

Evidence basis: Main method plus Appendices A–I.

Strengths

  • Frames repair at the correct state boundary: persistent memory and already-materialized execution consequences.
  • Uses explicit typed provenance and deterministic rules rather than hiding the central repair decision inside another opaque LLM call.
  • Independent-support checking prevents blanket deletion of affected-but-still-justified state.
  • Ablations cleanly expose the roles of the planner, support check, and selective replay.
  • Reports several unfavorable trade-offs—recurrence and controlled claim-F1—making the evidence easier to interpret.
  • Appendix detail is sufficiently rich to inform an implementation design or an independent benchmark reconstruction.

Limitations and red flags to retain

  • Diagnosis is out of scope: the method assumes the faulty-memory identifiers are already known.
  • Provenance is a prerequisite: missing or incorrect dependency edges directly threaten repair completeness/selectivity.
  • Side effects: rollback cannot undo arbitrary irreversible external actions without reset/idempotency/compensation support.
  • Benchmark selection: controlled cases are retained only when injection changes the final answer and creates downstream impact, so results do not describe natural fault prevalence.
  • Uncertainty: main results are single-run point estimates without confidence intervals.
  • Transfer scope: the adapted LongMemEval-V2 subset is selected, schema-converted, predominantly multi-fault, and poisoned-fault focused.
  • Durability: recurrence remains material; stale faults are especially weak in the per-fault slice.
  • Trace identification: on the controlled benchmark, LLM-judge and AgentTrace-style have higher claim-invalidation F1 than the proposed method.

Confidence in appraisal: moderate-high. The primary PDF provides unusually detailed methods and result tables, but the evidence remains preprint-stage, benchmark-based, and not externally reproduced in this artifact.

Implementation / practice takeaways

1 · Instrument provenance firstRecord typed memory reads/writes, citations/support, produced memories, mutations, supersession/derivation, and trace order at runtime. Post-hoc semantic guessing is not an equivalent substitute.
2 · Separate root disposition from descendant repairDelete the diagnosed source, but independently decide whether descendants should be preserved, quarantined, invalidated, or regenerated.
3 · Preserve only independent supportDo not let mutually contaminated descendants recursively validate one another. Require support from outside the affected region.
4 · Make rollback plans typed and validatableUse explicit disjoint action sets for memory deletion/quarantine and trace preserve/invalidate/replay decisions before computation begins.
5 · Replay the answer-relevant closureTarget the minimal executable subgraph needed to reconstruct the answer rather than replaying the entire trace by default.
6 · Regenerate final answersEven when many intermediate outputs survive support checking, regenerate the final answer under repaired state rather than preserving a possibly contaminated terminal response.
7 · Design tools for compensabilityIdempotent, resettable, or compensating tool interfaces turn rollback from a reasoning exercise into an operationally safe recovery mechanism.
8 · Measure state durability separatelyImmediate answer recovery is insufficient. Track recurrence after reloading repaired memory, benign-state preservation, claim invalidation quality, and repair cost.
Build-useful bottom line. The strongest reusable pattern is a transaction-like recovery layer for agents: typed lineage, contamination tracing, evidence-aware preservation, validated rollback plans, and selective replay. The method is most compelling as reliability infrastructure for systems that already capture high-fidelity execution provenance.
