One-page synthesis

Core thesis. NeSy-RAG converts each retrieved text chunk into an attributable Prolog module, exposes module functionality through 0-arity Boolean predicates, retrieves question-relevant predicates with joint natural-language/code embeddings, and executes a constrained Prolog query. Dynamic predicates represent user-specific facts; when their truth values are missing, symbolic execution triggers targeted follow-up questions rather than relying on the LLM to notice the information gap.

The paper targets three weaknesses of conventional RAG: reasoning steps that are difficult to audit, query construction that becomes unwieldy over growing symbolic knowledge bases, and failure to systematically identify missing user context. Its architectural move is to attach symbolic knowledge to the same chunk boundary used by retrieval, so a reasoning trace can map accessed facts and rules back to the originating chunk. Query generation is then narrowed to a top-k set of 0-arity predicates rather than the full knowledge base.

On ShARC, NeSy-RAG with gpt-oss:20b reaches 61.1% accuracy at k=10, compared with 42.8% for the same-model LLM RAG baseline. Mean duration is 7.4 s versus 11.4 s for that baseline. The strongest specific result is on the more class: NeSy-RAG correctly classifies 61% of these cases, versus 19% for LLM RAG and 23% for the LLM upper baseline. However, the system also over-asks: 31% of gold yes cases are predicted more. It retains false certainty in some missing-information cases, predicting yes for 17% and no for 15% of gold more instances. In addition, 178 executions (2.2%) fail because generated Prolog modules or queries are syntactically invalid.

Section condensation

Abstract

The authors frame standard RAG as better grounded than standalone generation but still opaque: intermediate reasoning cannot be reliably verified or attributed, and missing user-specific context is not systematically detected. NeSy-RAG synthesizes attributable Prolog modules from text chunks, retrieves 0-arity Boolean predicates using natural-language/code embeddings, composes Prolog queries, and invokes symbolic follow-up logic when user facts are missing.

The abstract reports 61.1% ShARC accuracy without domain-specific training versus 42.8% for a same-model RAG baseline. The claimed value is deterministic execution with transparent traces tied to source chunks and explicit knowledge-gap resolution.

1. Introduction

The introduction positions neuro-symbolic reasoning as complementary to RAG: LLMs provide extraction and translation from language, while symbolic execution provides deterministic inference and inspectable traces. The authors argue that prior approaches tend to use monolithic knowledge bases, manually curated rules, or generated programs without granular source attribution.

Four contributions are stated: modular attributable Prolog synthesis per retrieved chunk; 0-arity predicate abstraction for scalable query construction; symbolic missing-context detection with interactive follow-up; and ShARC evidence that the approach can outperform domain-agnostic LLM baselines.

2. Related Work

The paper connects to LLM-to-logic/code synthesis, Prolog reasoning proofs, medical rule generation, question-asking systems, symbolic retrieval, and Prolog-assisted QA. It distinguishes itself primarily through chunk-level attribution, dynamic user facts, and hierarchical retrieval of 0-arity predicates for query construction.

The literature positioning is plausible within the cited set, but the paper does not empirically compare against several cited neuro-symbolic systems. Related work therefore supports conceptual differentiation more than comparative performance.

3. NeSy-RAG Framework

NeSy-RAG is defined as a plug-in extension to an existing RAG system. Documents are chunked; an external retrieval method selects question-relevant chunks; each selected chunk has a paired Prolog module. The overall system is therefore explicitly contingent on the upstream domain knowledge and retrieval quality.

The question is assumed Boolean and is accompanied by potentially incomplete user-specific context. This assumption simplifies the interaction model and supports the paper's focus on decision-relevant missing facts, but it narrows the demonstrated task class.

3.1. Attributable Prolog Synthesis

For every retrieved chunk, an LLM synthesizes a separate Prolog module containing facts and rules derived from that chunk. Because each rule/fact lives in one module, the module identifier can serve as a provenance link back to the source chunk. Modules can also travel with chunks as retrieval metadata.

This local synthesis boundary is central to the design: it reduces the amount of source text presented during each synthesis call and avoids a single monolithic symbolic store. The paper asserts scalability benefits from this modularity, although large-corpus module management and cross-module consistency are not empirically evaluated.

3.2. Knowledge-Gap Detection

The system separates universal facts, whose arguments are fixed by domain knowledge, from dynamic facts whose values must be supplied at inference time. The prototype focuses on dynamic facts with a single Boolean argument. When a dynamic predicate is evaluated, a corresponding interaction method acquires or validates its value and asserts it into Prolog.

If the simulated user cannot provide the value, the prototype evaluates the unresolved predicate under both Boolean assignments. If the final query changes, the missing value is decision-relevant and the system returns more; if the outcome is invariant, it returns the stable yes/no answer. This is the strongest operational mechanism in the paper because it explicitly distinguishes missing data from missing data that actually matter to the decision.

3.3. Question Answering

At inference, retrieved text chunks bring their associated Prolog modules. A natural-language question must be translated into a query using predicates available in the retrieved modules. Execution yields a Prolog result and trace, and an LLM may translate the result into user-facing language.

The intended explanation chain is therefore source chunk → generated rule/fact → query predicate → Prolog execution trace → answer. This is more inspectable than free-form language reasoning, but correctness still depends on the fidelity and syntax of LLM-generated symbolic programs.

3.3.1. Query Translation

Instead of providing an LLM the complete knowledge base, NeSy-RAG adds 0-arity rules that expose a module's semantics as self-contained Boolean claims. These rules are embedded with a joint NL–PL model, ranked by cosine similarity to the question, and only the top-k rules are given to the query-generating LLM.

This creates a two-stage hierarchy: retrieve text chunks first, then retrieve candidate predicates within their paired modules. The LLM is constrained to compose a query only from retrieved 0-arity predicates. The approach reduces the generation search space, but the paper does not provide a component ablation that isolates the contribution of 0-arity abstraction, the code embedding model, or the query prompt.

3.3.2. Answer Generation

The paper adopts the prior pattern of converting the symbolic output into a natural-language answer. Its added distinction is that the Prolog trace carries module identity, enabling each accessed fact/rule to be mapped back to the source chunk and document.

The paper does not report a separate evaluation of explanation faithfulness, user comprehension, or attribution correctness. The architecture supports attribution by construction, but the quality of the synthesized rules remains a critical upstream dependency.

4. Experiments

The prototype is evaluated on ShARC, a conversational machine-reading benchmark derived from UK government legal text. Each test item contains a snippet, question, scenario/history/evidence, and one of four targets: yes, no, irrelevant, or more. The authors withhold the combined context and use a separate LLM as an idealized simulated user to answer generated follow-up questions.

All 8,276 test instances are used. Retrieval is simulated rather than implemented: the target snippet is presented alongside randomly sampled distractors, for a total of three candidate snippets. Because ShARC items rely on one relevant snippet, multi-hop retrieval is outside the evaluation.

4.1. Prototype Implementation

An LLM first classifies each candidate snippet as relevant or irrelevant. Relevant snippets receive reusable Prolog modules and 0-arity rules; all 0-arity predicates are embedded and ranked against the user question; the top-k set constrains LLM query composition. Returning None at relevance or query construction stages leads to irrelevant.

Modules are executed with SWI-Prolog, and dynamic predicates call a Python function via PySwip to obtain user answers. Dynamic-predicate values are cached within a conversation. When the user cannot answer, both Boolean assignments are tested for outcome sensitivity. This is concrete enough to reproduce the conceptual execution flow, although the paper does not report a public code repository or a full environment/configuration lockfile.

4.2. Baseline Implementations

The LLM upper baseline receives the target snippet, question, and complete user context and directly predicts the class; it approximates a domain-agnostic ceiling when all user information is already available. The LLM RAG baseline receives the same synthetic candidate set as NeSy-RAG, selects relevant snippets, predicts an answer, and—if it initially predicts more—generates follow-up questions before a second prediction.

These baselines are useful but not identical controls. The upper baseline has privileged context and no interactive burden. The trained BiAE result is also not directly comparable because it uses task-specific training and receives scenario/history directly.

4.3. Evaluation Results

NeSy-RAG uses gpt-oss:20b with jina-code-embeddings-1.5b; gpt-oss:20b runs on an RTX 3090 through Ollama. Accuracy is 60.0%, 61.1%, and 60.4% for k=3, 10, and 20, respectively; mean durations are 7.0, 7.4, and 7.3 s. Same-model LLM RAG reaches 42.8% at 11.4 s, while the gpt-5-mini RAG baseline reaches 53.7% at 25.1 s. Upper-baseline accuracies are 64.1% and 69.9%; trained BiAE is 77.9%.

NeSy-RAG's distinguishing result is improved recognition of unresolved information: 61% correct on gold more, versus 19% for same-model LLM RAG and 23% for the upper baseline. Its major error is over-conservatism—31% of gold yes becomes more. It also has 178 syntax-related execution errors (2.2%). No confidence intervals, significance tests, token-cost analysis, or full component ablations are reported.

5. Discussion and Conclusion

The authors conclude that modular Prolog synthesis, 0-arity predicate retrieval, and symbolic knowledge-gap detection jointly address opacity, query-scaling, and missing-context weaknesses in standard RAG. They emphasize reusability of compiled modules, smaller query-generation contexts, and algorithmic follow-up as explanations for the accuracy and runtime advantage over the same-model RAG baseline.

The paper's own future-work priorities align with its evaluation limits: reduce over-generation of dynamic predicates; test multi-hop and multi-chunk reasoning; and extend dynamic facts beyond Boolean arguments. The argument that conservative more behavior may be safer in high-stakes domains is reasonable as a design preference, but the paper does not evaluate clinical or other high-stakes deployment outcomes.

References

The bibliography situates NeSy-RAG among RAG trustworthiness, logic-program synthesis, Prolog-assisted QA, question-asking LLMs, and prior ShARC work. Individual references are not condensed here because they are supporting context rather than empirical evidence generated by this study.

Appendix A. Sample Prolog Knowledge Base

The appendix shows a generated module for the married-couple's-allowance example. Dynamic unary predicates encode user facts such as whether marriage allowance is claimed and whether the user/partner was born before a threshold date; derived 0-arity predicates encode eligibility, non-eligibility, answerability, and user-state claims.

The example makes the representation contract concrete: user information is Boolean, derived rules operate over those dynamic facts, and higher-level 0-arity predicates act as a semantic interface for query generation. It also demonstrates why synthesis errors are consequential: an incorrect or syntactically invalid rule becomes part of the executable decision path.

Appendix B. LLM Prompts

The paper provides prompts for Prolog module generation, 0-arity rule generation, constrained query generation, simulated-user predicate answering, baseline question answering, baseline follow-up generation, and relevance classification. The prompts require dynamic user facts to be unary Boolean predicates, derived rules to include positive/negative scenarios, query generation to use only available 0-arity predicates, and structured class outputs for the baselines.

Providing prompts materially improves reproducibility, but prompt availability does not substitute for released code, exact inference settings, random seeds, software versions, or failure-handling configuration. Those details are not fully reported in the paper.

Workflow — hierarchical query construction

User question
   ↓
1. Retrieve candidate text chunks from domain corpus
   ↓
2. Carry each chunk's pre-synthesized Prolog module with it
   ↓
3. Extract 0-arity Boolean interface predicates from retrieved modules
   ↓
4. Embed question + predicates in joint NL–PL space
   ↓
5. Rank predicates by cosine similarity; retain top-k
   ↓
6. LLM composes query using only those predicates
   ↓
7. Execute query in Prolog and expose trace + source-module provenance

Algorithm — decision-relevant knowledge gap

When Prolog evaluates an unknown dynamic Boolean predicate:
  ask the user / simulated user for its value
  if value is known:
      assert it and continue
  else:
      evaluate the query with predicate = true
      evaluate the query with predicate = false
      if outcomes differ:
          return MORE   # the missing fact can change the answer
      else:
          return stable YES/NO outcome
Why this matters. The procedure is a small but transferable pattern: sufficiency can be tested by counterfactual outcome sensitivity rather than by a generic “missing field” check. That is potentially useful anywhere a decision service must distinguish incomplete data from consequentially incomplete data.

Strengths

  • Clear separation of language processing from deterministic execution.
  • Provenance is designed into the symbolic representation boundary rather than added after generation.
  • Knowledge-gap detection has an explicit decision test rather than relying on LLM self-awareness.
  • The authors expose a meaningful failure pattern instead of reporting aggregate accuracy alone.
  • Prompt and Prolog appendices make the implementation concept unusually concrete for a short systems paper.

Limitations and claim boundaries

  • Retrieval scalability is claimed more than tested. The experiment supplies three candidates and does not implement a corpus retrieval benchmark.
  • Multi-hop/inter-module reasoning is untested. ShARC's single-relevant-snippet structure avoids a central challenge of modular symbolic systems.
  • Semantic synthesis accuracy is not directly measured. Syntax failures are counted, but incorrect-yet-valid Prolog translations are not separately quantified.
  • Attribution quality is architectural, not empirically validated. A trace can identify which generated rule was executed, but that does not prove the rule faithfully represents its source text.
  • High-stakes safety is not established. The claim that conservative more behavior may be safer is a reasonable hypothesis, not a tested safety outcome.
  • Cost/efficiency evidence is incomplete. Runtime is reported, but token usage and module-synthesis amortization are not systematically measured.

Implementation / practice takeaways

BuildStore a compiled reasoning artifact beside each source chunk, with an immutable source anchor and version. Treat provenance as part of the executable object.
BuildSeparate universal/domain facts from dynamic/user facts. Make the latter typed, explicit, and queryable rather than leaving them buried in prompt context.
BuildAdd a sufficiency service that tests whether unknown values can change the result. Ask for data only when the decision is sensitive to them.
BuildConstrain query-generation vocabulary. Retrieve a small set of semantic interfaces/predicates first, then allow the LLM to compose only from that set.
GuardrailValidate generated symbolic code both syntactically and semantically before it can participate in decisions. The paper's 2.2% syntax failure rate shows why compilation alone is insufficient.
GuardrailDistinguish traceability from faithfulness: “this rule came from chunk X” is not enough; the rule-to-source transformation itself needs validation.
Test nextUse real retrieval, conflicting/multi-source evidence, multi-hop queries, non-Boolean missing values, and adversarial or ambiguous source text.
Do not overclaimDo not infer clinical safety, general RAG superiority, or large-corpus scalability from this ShARC experiment.
Highest-value pattern to reuse: the counterfactual sufficiency test. When a required fact is unknown, evaluate the decision under each admissible value; only interrupt the user if the decision changes. This converts “missing data handling” into an explicit reasoning service.
