One-page synthesis

Core thesis: For private enterprise KGs, the most reliable path to Text-to-Cypher training data is to build executable Cypher from observed graph facts first, then use LLMs for language diversification and judging, and serve a LoRA-tuned generator with class-conditioned schema prompting plus entity candidates.
Why it matters

Prompt-only LLMs can produce syntactically valid Cypher while returning the wrong graph results. The paper makes execution-result F1, not execution rate alone, the central user-facing metric.

Most reusable idea

Use the KG itself as a supervision source: sample real relation patterns, fetch subgraphs, deterministically construct gold Cypher, and only then generate natural-language variants.

Most important result

In the final 11-class setting, the system reports 95.2% exact match, 99.9% execution rate, and 0.964 execution-result F1.

Key limitation

The KG, schemas, APIs, generated data, checkpoints, and real identifiers are proprietary. The result is operationally suggestive but not independently reproducible.

High-yield interpretation

KG2Cypher is best read as an enterprise structured-query construction pattern rather than a general public benchmark. The valuable pattern is the staged constraint stack: graph-derived symbolic targets, LLM language diversification with deterministic semantic checks, calibrated LLM/human validation, candidate-aware SFT, and class-conditioned serving when relation retrieval is unreliable.

The strongest evidence is internal consistency across diagnostics: prompt-only execution is high but answer quality is poor; relation retrieval is the bottleneck; SFT improves execution-result F1; and class-conditioned schema prompting avoids low-recall relation retrieval. The weakest point is external validity: all decisive assets are private, the setting is Korean enterprise search, and only one generator backbone is evaluated.

Section condensation

Abstract

KG2Cypher addresses the cost of building natural-language interfaces for private enterprise knowledge graphs. The core move is data-centric: construct executable Cypher from observed graph facts first, then use LLMs to generate the corresponding natural-language question, validate the pair, and convert it into candidate-aware supervised fine-tuning data.

The reported evaluation is in Korean enterprise settings where short search-style queries, schema paraphrases, URI binding, and literal sub-fields make grounding difficult. LoRA SFT improves execution-result F1 from 0.806 to 0.950 for broadcast-program queries and from 0.70 to 0.92 for company queries; the final 11-class class-conditioned system reports 95.2% exact match, 99.9% execution rate, and 0.964 execution-result F1.

1. Introduction

The paper frames enterprise KGs as useful but inaccessible to non-expert users because graph users usually do not know the available node types, relation types, Cypher syntax, or internal entity IDs. Text-to-Cypher is presented as a constrained structured-query problem requiring valid schema relations, graph patterns, entity URI binding, literal sub-field selection, and execution against a live graph database.

The authors argue that manual text-Cypher annotation does not scale across enterprise domains, and prompt-only LLM use can produce syntactically executable but semantically wrong Cypher. Their central hypothesis is that an enterprise can reuse its own KG as the supervision source: sample real relation patterns, fetch subgraphs, deterministically build executable Cypher targets, and reserve LLMs for language-side generation and judging.

2. Related Work

The related-work section situates KG2Cypher within structured query generation, especially text-to-SQL, KGQA logical-form generation, schema linking, constrained decoding, and LLM prompting. It also positions Cypher as an industrial property-graph query language with emerging public Text-to-Cypher resources.

The paper distinguishes KG2Cypher from public benchmarks and synthetic Cypher resources by focusing on private enterprise KGs whose identifiers, schemas, entity APIs, generated data, and evaluation artifacts cannot be released. The contribution is therefore less a public benchmark and more a production-oriented data construction, training, and serving pattern for private graph search.

3.1 Task Formulation

The generation task is formalized as y = fθ(q, R, E), where a model receives a natural-language question, relation candidates, and entity candidates, then emits executable Cypher. The relation candidates carry subject class, object class, predicate identifier, and linguistic hints; entity candidates carry an internal URI, display name, and class label.

This formulation intentionally aligns supervised training with deployment. The model should select among provided schema and entity candidates rather than invent private identifiers or unsupported schema elements from free text alone.

3.2 System Overview

The system separates symbolic construction from language generation. KG2Cypher builds Cypher targets using deterministic code over graph values and uses LLMs for paraphrasing, compressed query generation, and validation rather than asking the LLM to invent graph structure.

The workflow has three main arcs: KG-grounded data construction, candidate-aware SFT, and class-conditioned serving. This is the paper’s main design principle: constrain the LLM with graph-derived targets and inference-like candidates so errors shift from schema hallucination toward measurable candidate selection and generation quality.

3.3 Predicate Collection and Filtering

Instead of relying only on static schema files, KG2Cypher inspects graph instances to collect subject-predicate-object patterns that actually appear in the KG. For broadcast programs, examples include relations such as broadcast_by, genre, and number_of_episodes, with object type recorded as entity or literal.

Rule-based filtering removes non-searchable or metadata-like fields such as geocoordinates, media URLs, social-media IDs, and system fields. Relation identifiers with equivalent query semantics are merged to reduce redundant or misleading supervision.

3.4 Skeleton Sampling and Subgraph Fetching

Filtered relations are sampled into query skeletons with a 40/30/20/10 distribution for one-, two-, three-, and four-relation structures. Candidate skeletons are validated against Memgraph through a LIMIT 1 query before data generation proceeds.

For each valid skeleton, the pipeline samples up to 50 matching subgraphs. This cap is an anti-bias mechanism: it prevents frequent graph patterns from dominating the generated dataset while still grounding each example in real entity URIs, literal values, and relation attributes.

3.5 Canonical Cypher Construction

KG2Cypher deterministically constructs Cgold from each fetched subgraph. Entity nodes are bound by unique graph identifiers in WHERE clauses, and literals are mapped to schema-specific attributes with comparison operators in {=, >, <, >=, <=}.

The same symbolic conditions are also rendered as an analyzed intermediate form and a template-derived naive natural-language statement. These synchronized representations keep the later LLM rewriting step anchored to the verified graph structure and literal constraints.

3.6 LLM-Based Language Diversification

The LLM receives Cgold, analyzed and naive language forms, ontology constraints, and target-language synonym maps. The symbolic Cypher target remains fixed; the LLM rewrites only the language side, reducing the risk of unsupported graph structures or changed literal semantics.

The paper reports three language-output types: one term-preserving question, five paraphrases, and compressed search-style queries for shallow skeletons with up to three joins. Numeric and date relations receive deterministic checks to verify that units and comparison words still match the Cypher condition.

3.7 LLM Judge and Human Validation

A gpt-oss-120B judge scores generated pairs on a 0/1/2 scale across faithfulness to Cgold, target-language fluency, and completeness of schema constraints. Passing examples enter the training set; imperfect rows are routed to a human validation interface for keep/edit decisions.

The scoring guide is calibrated on 200 human-annotated samples with MAE, adjacent agreement, and deduction catch rate rather than a single metric. The authors revise the guide using human disagreement comments and report that faithfulness MAE drops from 0.314 to 0.251 after three iterations.

3.8 Candidate-Aware SFT Construction

Validated text-Cypher pairs are converted into instruction-style examples containing the question, candidate relations, entity candidates, and gold Cypher output. Candidate relation records include classes, predicate identifiers, and linguistic hints; candidate entity records include URI, display name, class, and retrieval distractors.

This is an important implementation detail: the training input mirrors the inference-time prompt. The model learns to tolerate realistic retrieval noise and select necessary relations and entity URIs instead of relying on clean oracle-only inputs.

3.9 Class-Conditioned Schema Prompting

The paper rejects relation-first retrieval for its enterprise setting because the available relation API has low recall and missing gold relations are usually unrecoverable by the generator. Entity retrieval is considered reliable enough to supply URI candidates, so the system uses a domain classifier to choose the graph class and then inserts the full class schema into the prompt.

The domain classifier is KLUE-BERT-base trained for 11-way single-label classification. This shifts the retrieval burden from relation-level ranking to class routing plus entity disambiguation and keeps the prompt bounded by the selected class schema.

3.10 Training and Serving

The generator is Llama-3.1-8B-Instruct adapted with LoRA. The final adapter trains about 41M parameters, around 0.52% of the base model, with prompt tokens masked so the loss applies only to the assistant-side Cypher response.

At inference, the service classifies the domain, loads the class schema, runs NER, retrieves entity candidates, builds a candidate-aware prompt, and generates Cypher through vLLM. The backbone stays loaded; NER uses the base model without LoRA, and Cypher generation attaches the LoRA adapter at request time to avoid separate large-model endpoints.

4.1 Data and Metrics

The evaluation uses internal Korean enterprise KG domains. The final class-conditioned setting spans 11 graph classes with 20,745 training, 2,590 development, and 2,621 test examples; the paper also reports broadcast and company diagnostics for prompt-only behavior, retrieval, SFT, and transfer.

Metrics are exact match, execution rate, and execution-result F1. The authors emphasize execution-result F1 because executable Cypher can still return wrong answer sets, making execution validity alone a misleading deployment metric.

4.2 LLM Judge Calibration

The initial judge prompt passes fluency and completeness but fails faithfulness calibration, with faithfulness MAE 0.314 against human labels. This matters because the judge is used as a quality gate for synthetic training data.

After automatic scoring-guide revision using human disagreement comments, the guide grows from 270 to 325 lines and stabilizes. Faithfulness MAE falls to 0.251, below the stated 0.27 target, allowing high-confidence examples to be accepted and lower-confidence cases to be sent to human validation.

4.3 Prompt-Only Diagnostics

Prompt-only gpt-oss-120B diagnostics show that runnable Cypher is not enough. Rules-only and few-shot prompts achieve near-zero execution-result F1 despite 100% execution, and adding the full broadcast schema improves F1 only to 0.0655.

Even an oracle prompt with gold relation and entity candidates reaches only 47.7% exact match and 0.7139 F1. The recurring failure modes are hallucinated private entity URIs, plausible but wrong relation choices, and incorrect literal sub-fields such as value_number versus date-related fields.

4.4 Retrieval Diagnostics

Entity retrieval performs much better than relation retrieval in the reported service APIs. Entity recall reaches 67.5% at k=1, 87.5% at k=5, and 95.0% at k=20 on searchable entity mentions.

The deployed relation API reaches only 40.6% recall@20, and query rewriting raises it only to 49.8%. This is the empirical basis for class-conditioned schema prompting: if relation retrieval omits the gold relation, generation usually cannot recover.

4.5 LoRA SFT and Class-Conditioned Results

LoRA SFT substantially improves generation quality over prompt-only baselines with gold candidates. Broadcast execution-result F1 rises from 0.806 to 0.950; company F1 rises from 0.70 to 0.92; a broadcast-trained adapter transfers partly to company with OOD F1 0.79 but remains below in-domain SFT.

The final 11-class setting uses a KLUE-BERT-base classifier with reported 99.66% accuracy and supplies the predicted class schema to the generator. It reports 95.2% exact match, 99.9% execution rate, and 0.964 execution-result F1, supporting the class-conditioned design inside this proprietary environment.

5. Conclusion

The paper concludes that KG2Cypher can turn observed enterprise graph facts into executable training targets, use LLMs only for language and validation, and train a candidate-aware LoRA generator for production-style prompts.

The main practical conclusion is that KG-grounded SFT plus class-conditioned schema prompting can overcome the observed prompt-only and relation-retrieval bottlenecks. This is a credible design pattern, but not a directly reproducible result because the core KG, APIs, data, and checkpoints are private.

6. Limitations

The largest limitation is opacity: the KG, entity APIs, generated data, and model checkpoints are proprietary, so the paper reports aggregate statistics and anonymized examples rather than releaseable artifacts. The pipeline also cannot create supervision for relations, entities, or values missing from the KG.

The current instantiation is Korean and includes language-specific question prompts, judge calibration data, and domain classification modules. Deployment still depends on domain classification, NER, entity retrieval, and entity disambiguation; outside entities and homonyms remain difficult. Only Llama-3.1-8B-Instruct is evaluated as the generator backbone.

Ethical Considerations

The system is intended for authorized enterprise KG search and analytics. Because internal KGs may contain proprietary or sensitive business information, the authors state that generated data, execution logs, and model outputs require organizational access control and data-governance policies.

Human validation is positioned as a semantic-drift control. The paper anonymizes examples and translates Korean text for readability, but the operational safety case would still require local governance for schema access, log retention, model output auditing, and permission boundaries.

Appendices A-I

The appendices supply details that materially affect interpretation: judge-metric validation, an execution-result F1 example, prompt-only failure modes, class labels, oracle prompting by relation count, SFT diagnostics under candidate noise, training hyperparameters, data-construction examples, and a candidate-aware SFT instance.

The appendix material strengthens implementation usefulness because it exposes why the authors chose multiple judge metrics, why query complexity matters, how distractor candidates affect SFT, and what information appears in a training/serving prompt. It does not remove the reproducibility limitation because real schemas, entities, data, and code remain unavailable.

Workflow / algorithm extraction

WORKFLOW - KG2Cypher data construction and serving

Inputs:
  - Existing enterprise knowledge graph with observed subject-predicate-object patterns.
  - Entity and literal graph values; class schemas; target-language synonym maps.
  - Entity retrieval API; domain classifier; generator backbone and LoRA adapter.

Process / decision rules:
  1. Inspect graph instances to collect active SPO patterns and filter metadata/non-searchable attributes.
  2. Sample one- to four-relation query skeletons with 40/30/20/10 distribution.
  3. Validate skeletons against Memgraph with LIMIT 1 and sample up to 50 matching subgraphs.
  4. Deterministically construct canonical Cypher from real graph IDs, relations, literals, and comparison operators.
  5. Generate language variants with LLMs while keeping the Cypher target fixed.
  6. Apply deterministic checks for numeric/date unit and comparison consistency.
  7. Use calibrated LLM judge plus human validation to accept, review, or edit pairs.
  8. Convert accepted pairs into candidate-aware SFT examples with relation/entity candidates and retrieval distractors.
  9. Serve by classifying the domain, inserting the full class schema, retrieving entity candidates, generating Cypher with LoRA, and executing on Memgraph.

Outputs:
  - Validated Text-Cypher pairs.
  - Candidate-aware LoRA SFT dataset.
  - Production-style Text-to-Cypher generation pipeline.

Failure modes:
  - Missing KG facts cannot generate supervision.
  - Low-recall relation retrieval can omit needed schema items.
  - Entity homonyms and outside entities can produce URI-binding errors.
  - Literal sub-field errors can produce executable but semantically wrong Cypher.
  - Domain classifier errors can insert the wrong class schema.

Human review:
  - Needed for judge calibration, semantic-drift correction, and low-confidence generated pairs.

Governance:
  - Requires access controls for private KGs, generated data, execution logs, prompts, and outputs.
  - Needs schema-version tracking, retrieval monitoring, judge drift checks, and audit trails for generated queries.

AI/ML appraisal add-on

Task

Natural-language-to-Cypher generation over private enterprise property graphs with URI binding, schema relation selection, literal handling, and execution against Memgraph.

Data

Internal Korean enterprise KG domains; final 11-class setting uses 20,745 train, 2,590 dev, and 2,621 test examples. Public data are not released.

Method

Graph-first target construction, LLM language diversification, calibrated LLM judge plus human validation, candidate-aware LoRA SFT, and class-conditioned serving.

Baselines

Prompt-only gpt-oss-120B under rules, few-shot, schema, and oracle candidate conditions; in-domain and out-of-domain LoRA comparisons.

Metrics

Exact match, execution rate, execution-result F1, retrieval recall@k, classifier accuracy, judge MAE/adjacent agreement/catch rate.

Leakage / contamination

Not fully assessable from the paper. The pipeline uses generated data from the same proprietary KGs being evaluated, so split construction and overlap controls are important but not deeply detailed.

Ablations

Prompt-only variants, relation/entity retrieval diagnostics, query-complexity breakdown, candidate noise and schema-format diagnostics, OOD transfer from broadcast to company.

Reproducibility

Training hyperparameters and examples are given, but core data, schemas, APIs, prompts, checkpoints, code, and identifiers are unavailable.

Do not overclaim: The final 0.964 execution-result F1 supports this specific internal pipeline and evaluation setting. It does not prove general Text-to-Cypher performance on arbitrary graph databases, languages, schemas, or entity APIs.

Evaluation and appraisal

Verdict: Read first for enterprise KG/RAG query-system design, candidate-aware SFT, and deterministic data-generation patterns. Use as a design reference and evaluation warning, not as externally validated evidence that the exact performance will transfer.

  • Retrieval realism: measures entity and relation recall separately and designs serving around observed relation-retrieval failure.
  • Training-serving alignment: candidate-aware SFT includes relation/entity candidates and distractors that resemble inference-time prompts.
  • Judge calibration: validates LLM judge behavior against human labels with multiple metrics rather than trusting the judge by default.

Main limitations

  • Proprietary opacity: data, schemas, entity APIs, prompts, code, checkpoints, and identifiers are unavailable.
  • External validity: evaluation is Korean enterprise-specific, and language-facing components require adaptation elsewhere.
  • Limited model coverage: generator experiments center on Llama-3.1-8B-Instruct with LoRA.
  • Incomplete operational reporting: latency, cost, monitoring, schema versioning, human-review burden, and security controls are not quantified in depth.
  • Potential split/coverage questions: generated data from the same KG ecosystem require careful split and leakage controls; the paper does not fully expose these mechanics.

Bottom line

KG2Cypher is a high-value design reference for teams building private graph query systems. The most transferable lesson is not the reported exact-match score; it is the pipeline discipline of turning real graph facts into executable targets, keeping LLMs away from unsupported symbolic construction, aligning SFT with inference-time candidates, and evaluating answer-set correctness rather than executable syntax alone.

Confidence in appraisal: Moderate. The paper is internally coherent and provides enough methodological detail to inform design, but core artifacts are proprietary and independent reproduction is not possible from the public preprint.

Implementation / practice takeaways

Build

For private KGs, start with graph-derived Cypher targets: sample observed relations, execute skeletons, fetch real subgraphs, and construct canonical queries deterministically.

Train

Make SFT examples candidate-aware. Include candidate relations, entity candidates, and realistic distractors so training resembles serving.

Serve

Measure relation and entity retrieval separately. If relation recall is low, consider class-conditioned full-schema prompting instead of relation-first retrieval.

Evaluate

Report execution-result F1 or answer-set agreement. Execution rate can look excellent while generated queries return wrong results.

Validate

Calibrate LLM judges against human labels using multiple metrics. Route low-confidence or drift-prone examples to human review.

Govern

Version schemas, prompts, entity APIs, and LoRA adapters. Log generated Cypher, execution results, review decisions, and schema changes under enterprise access controls.
