Scope: this protocol defines the expected structure, reasoning discipline, extraction granularity, and appraisal standards for future reference HTML files. It is not a substitute for primary-source reading, clinical judgment, regulatory review, or local policy.

One-page protocol synthesis

Core standard: each reference HTML file should make the source easier to retain, search, critique, and reuse. The file should not merely summarize. It should separate what the source says, how the source supports it, what the visuals and tables contain, how credible the work is, and what should be done with it next.

The reference file should follow a stable layout: metadata, one-page synthesis, section condensation, figure/table breakdowns, evaluation and appraisal, implementation or practice takeaways, and quality caveats. This layout supports rapid reading now and later reuse in notes, RAG systems, protocols, teaching files, and research triage.

The default compression rule is strict: condense each source section into no more than two paragraphs, while preserving all load-bearing claims, methods, measurements, limitations, and conclusions. Visuals, tables, algorithms, workflows, and diagrams should be decomposed into separate structured text or code blocks because they often contain the most reusable information.

End-to-end workflow

1. Identify the source and classify the artifact

Determine whether the source is a preprint, peer-reviewed article, clinical guideline, regulatory document, benchmark paper, technical report, protocol, narrative review, systematic review, dataset paper, software paper, or practice document. The source type controls the appraisal lens: a benchmark paper should be judged differently than a clinical guideline or pharmacokinetic study.

Extract bibliographic metadata first: title, authors, year/date, venue or repository, version, DOI/arXiv/PubMed identifier when available, topic area, and source URL. If the source is a preprint, explicitly label it as such. If the source is a living guideline or current practice document, verify currency where feasible.

2. Read for structure before summarizing content

Map the document before writing: abstract, introduction/background, methods, results, figures, tables, discussion, limitations, conclusion, appendices, and supplementary materials. For non-IMRaD documents, map the actual headings rather than forcing the source into a generic structure.

Identify the load-bearing sections: methods, experimental setup, validation plan, inclusion/exclusion criteria, statistical analysis, benchmark design, clinical recommendations, safety constraints, and limitations. These should receive more attention than background or promotional framing.

3. Separate summary from appraisal

Summary should report what the source claims without premature judgment. Appraisal should then evaluate whether those claims are well supported. This prevents the final file from blending author claims, assistant interpretation, and independent critique into one ambiguous narrative.

Use explicit labels: “Core thesis,” “What the authors did,” “What the results show,” “What the source does not establish,” “Major limitations,” and “Bottom-line appraisal.” When the source is weak, say so directly without overstating certainty.

4. Preserve reusable structure

Every reference file should be useful months later without reopening the source. Preserve identifiers, study population, intervention/exposure/model, comparator/baseline, outcome/metric, dataset, protocol, statistics, major caveats, figure contents, table contents, and implementation implications.

Prefer structured blocks over prose for workflows, algorithms, benchmark setups, clinical pathways, schema definitions, drug regimens, eligibility criteria, and figure decompositions. This makes the file easier to search, convert, index, or reuse in a retrieval system.

Grounding hierarchy

GROUNDING PRIORITY

1. User-provided source or uploaded file
   - Treat as the primary object for summary.
   - Do not replace it with outside commentary unless asked.

2. Source metadata pages
   - Use to verify title, authors, date, version, abstract, DOI, PMID, arXiv ID, or errata.

3. Primary full text, PDF, supplementary appendix, trial registry, code repository, dataset card
   - Use when appraisal depends on methods, figures, appendices, or implementation details.

4. Guidelines, labels, society statements, or regulatory sources
   - Use for clinical or practice claims that could affect care.

5. Secondary commentary
   - Use only when the task asks for reception, controversy, user sentiment, implementation experience, or broader context.
Currency rule: for clinical practice, guidelines, drug information, regulatory status, pricing, software, benchmarks, AI model capabilities, and current events, verify recency when possible. A source can be accurately summarized and still be outdated for practice.

Section condensation rules

Default compression rule: every source section receives a maximum of two paragraphs unless the user explicitly requests greater depth. Each paragraph should be dense enough to preserve the section’s function, claims, methods, results, and caveats without becoming a paraphrased wall of text.

Section-by-section method

Section typeWhat to preserveWhat to avoid
AbstractProblem, method, main result, claimed implicationRepeating author framing without later verification
Introduction / BackgroundWhy the work exists, gap claimed by authors, clinical/scientific contextOverweighting background as evidence
MethodsDesign, population/data, inclusion/exclusion, model, intervention, comparator, endpoints, statistics, validationVague statements such as “standard methods were used”
ResultsPrimary outcomes, effect sizes, uncertainty, tables, subgroup results, benchmark deltas, ablationsOnly reporting directionality without magnitude
DiscussionAuthors’ interpretation, implications, limitations acknowledgedAccepting speculation as established fact
LimitationsInternal, external, statistical, operational, regulatory, safety, and generalizability limitsHiding limitations in an appraisal paragraph only
ConclusionFinal claim and justified next stepLetting conclusion inflate weak evidence

Preferred section block format

<div class="section-summary">
  <h3>Section heading from source</h3>
  <p>Paragraph 1: what this section says and why it matters.</p>
  <p>Paragraph 2: key details, constraints, results, or limitations.</p>
</div>

Compression discipline

  • Do not flatten structure: preserve headings, named methods, numbered frameworks, study arms, metrics, and timepoints.
  • Do not bury caveats: limitations belong near the claims they weaken and again in the appraisal section.
  • Preserve magnitude: include effect sizes, rates, sample sizes, confidence intervals, p values, calibration, accuracy, latency, or benchmark scores when central.
  • Separate author claim from inference: phrase uncertain conclusions as “the authors argue,” “the study suggests,” or “this supports but does not prove.”
  • Use plain labels: “Not tested,” “Not reported,” “Unclear,” and “Out of scope” are better than vague prose.

Visual appraisal questions

  • Does the figure report the denominator, sample size, uncertainty, and scale?
  • Are axis labels, units, time windows, and thresholds clear?
  • Does the visual support the claim made in the text, or is it mainly conceptual?
  • Could the same pattern be explained by confounding, selection bias, leakage, cherry-picking, or calibration failure?
  • For AI/ML figures, does the figure separate training, validation, test, external validation, ablation, and deployment?
  • For clinical figures, does the figure distinguish surrogate outcomes from patient-centered outcomes?

Evaluation and appraisal rubric

Appraisal standard: the final verdict should answer three questions: Is the source worth reading? How much should we trust it? What practical use, if any, should it have?

Core appraisal dimensions

Relevance
0–10
Fit to the user’s clinical, research, AI/ML, workflow, or implementation interests.
Novelty
0–10
How much the work adds beyond known methods, guidelines, or prior systems.
Method strength
0–10
Appropriateness of design, controls, statistics, validation, and comparison groups.
Evidence strength
0–10
How directly the data support the claims and whether uncertainty is reported.
External validity
0–10
Generalizability across sites, populations, datasets, tasks, or practice environments.
Implementation value
0–10
Whether the work gives enough detail to change a workflow, build a tool, or inform practice.

Score bandClinical / scientific sourceAI/ML / systems source

Red flags

  • Claim inflation: abstract or conclusion overstates what the data actually establish.
  • Missing denominator: rates are reported without sample size, eligibility, missingness, or denominators.
  • Surrogate substitution: surrogate endpoints are presented as if they prove patient-centered benefit.
  • Benchmark leakage: test data may overlap with training, tuning, prompt development, or example selection.
  • Weak comparator: the source compares against outdated, poorly tuned, or irrelevant baselines.
  • No failure analysis: errors, harms, negative results, override cases, or subgroup failures are not examined.
  • No implementation path: strong claims but no schema, code, protocol, operational steps, or validation plan.
  • Regulatory/practice ambiguity: clinical or safety-relevant claims without discussion of oversight, monitoring, liability, or local constraints.

Domain-specific appraisal modules

Use the core structure for every file, then add the relevant module below. Do not force every paper through every module.

Clinical trials
PICO + validity + patient-centered outcomes

Extract population, intervention, comparator, outcomes, duration, randomization, blinding, attrition, adverse events, effect size, NNT/NNH when possible, and external validity.

Pharmacotherapy
Dose, PK/PD, safety, monitoring

Preserve dose, route, renal/hepatic adjustment, exposure metrics, MIC/target attainment when relevant, interactions, contraindications, monitoring, and guideline/label alignment.

Guidelines
Recommendation strength + applicability

Extract recommendation wording, evidence grade, population, exclusions, implementation notes, controversies, and differences from prior guidance.

Systematic reviews
Search, selection, heterogeneity, certainty

Extract search dates, databases, inclusion/exclusion, risk of bias, heterogeneity, publication bias, GRADE certainty, pooled estimates, and clinical applicability.

AI/ML benchmarks
Task, data, baselines, leakage, reproducibility

Extract datasets, splits, metrics, baselines, prompts, tool use, contamination risk, ablations, compute, reproducibility, error modes, and deployment relevance.

Agent / RAG systems
Evidence path + state + verification

Extract tools, retrieval corpus, context policy, state management, verifier design, citation rules, trace logging, fallback behavior, and failure analysis.

Parser / extraction papers
Input heterogeneity + schema fidelity

Extract supported formats, layout handling, table/figure extraction, citation preservation, schema, evaluation fixtures, error taxonomy, and downstream use cases.

Practice workflows
Operational feasibility + risk controls

Extract trigger, actors, handoffs, required data, decision points, escalation, downtime, documentation, audit trail, and measurable outcomes.

Style standards

  • Use a single-file HTML document with embedded CSS.
  • Use card-based sections with clear borders, readable spacing, and print-friendly CSS.
  • Use metadata grids for quick facts and rating grids for appraisal.
  • Use dark code blocks for structured figure/table/workflow extraction.
  • Use colored callouts sparingly: blue for verdict/core thesis, amber for caution, red for major concern, green for strong practical takeaway.
  • Make the document readable without external fonts, JavaScript, remote images, or external CSS.
  • Prefer semantic HTML: header, main, nav, section, table, footer.

- Provide a one-page synthesis.
- Condense each section into no more than two paragraphs.
- Break down all figures, tables, algorithms, workflows, and important visuals in separate structured text/code blocks.

Quality-control checklist

Pass condition: the finished file should allow a reader to understand the source’s claim, evidence, visual content, weaknesses, and practical relevance without reopening the original document immediately.

Pre-output checks

  • Metadata complete: title, source type, date/version, authors/organization, and source identifier are included when available.
  • Scope clear: the file states whether the source is a preprint, conceptual proposal, validated study, guideline, benchmark, or practice document.
  • Sections preserved: each original section is represented, or omissions are explicitly noted.
  • Two-paragraph limit followed: section summaries are concise unless the user asked for greater detail.
  • Visuals decomposed: figures, tables, algorithms, and workflows have separate structured blocks.
  • Magnitude preserved: key sample sizes, metrics, effect sizes, uncertainty, benchmark deltas, and thresholds are included when central.
  • Claims separated from appraisal: author claims are not presented as independently established unless evidence supports them.
  • Limitations explicit: methodological, statistical, clinical, operational, and generalization limits are not hidden.
  • Actionability stated: the file says how to use the source: read first, read soon, skim, implement, monitor, avoid, or treat as background.
  • HTML self-contained: no external dependencies, readable styling, working anchors, and print-friendly behavior.

Failure modes to prevent

Avoid producing a polished-looking file that is only a superficial abstract expansion. The reference file must preserve methods, visuals, quantitative results, limitations, and appraisal. Aesthetic quality should support evidence quality, not conceal weak extraction.
