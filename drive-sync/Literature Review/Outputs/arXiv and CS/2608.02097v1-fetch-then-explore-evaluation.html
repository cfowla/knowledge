Core thesis. Search agents should not be forced to extract a final reading at the moment they select a page. FTE separates selection from extraction: fetch saves the full normalized page off-context, while grep and read retrieve bounded evidence later. Because pages persist across the trajectory, the agent can return to prior evidence after its hypothesis changes.

What the results show. Under a fixed ReAct harness, search backend, crawler, and backbone, FTE is best on BrowseComp for all three tested models (44.5%, 52.5%, and 70.5% accuracy). On WideSearch it is essentially tied with the strongest visit-summary baseline: −1.2, +0.3, and −0.1 Row-F1 across the three backbones. The clearest behavioral distinction is revisitability: FTE reuses 67–76% of WideSearch documents after leaving them, versus less than 9% for transient interfaces.

Main reservation. The paper reports the best of three runs, gives no confidence intervals or paired significance tests, and uses only 200 of 1,266 BrowseComp questions. Several claimed advantages over OPEN+FIND are only 4–9 extra correct questions out of 200. The design is convincing enough to build and test, but not strong enough to treat the exact effect size as settled.

Section-by-section condensation

Abstract and Introduction

The paper identifies a neglected interface problem in long-horizon web agents. Visit-and-read systems immediately compress a selected page into context, forcing extraction before the agent knows which fact will matter. Stateful browsing separates opening from finding but retains only one page, so prior pages disappear when the agent moves on.

FTE stores every selected page in a per-question filesystem cache and returns only a lightweight path/size record. Evidence is extracted later with bounded tools. The authors claim three benefits: low-context-cost selection, deferred/repeatable extraction, and retention across the trajectory.

Related Work

The paper positions FTE against long-horizon deep-research agents, context-management methods, filesystem-based coding agents, agent-memory systems, state-externalizing search harnesses, direct corpus interaction, and pre-neural select-then-extract QA pipelines. Its claimed niche is narrow: isolate the storage/document interface without adding training, curation agents, or a pre-existing closed corpus.

The novelty claim is reasonable but should be read as a controlled systems decomposition, not a fundamentally new memory primitive. Several adjacent systems already externalize state; FTE’s strongest contribution is the focused comparison against visit-and-read and transient browsing.

Method: Agent model and FTE tool profile

All profiles run inside the same ReAct loop. The action set is fixed search tools, one profile-specific document toolset, and a terminal answer. This design holds the model, search backend, prompt, and harness constant so performance differences can be attributed more directly to document access.

FTE uses a private temporary directory per question. fetch(url) normalizes and stores the full page but returns only path, character count, and cache status. grep(pattern, path?, context?) can search all cached files or one file and returns up to 20 line-numbered matches. read(path, offset, limit) returns at most 200 lines and approximately 50 KB. list_fetched() enumerates the cache.

Design space and baselines

The profiles differ along substrate, extraction timing, and query scope. SNIPPET-ONLY provides no document access. VISIT-SNIPPET and VISIT-SUMMARY place a fixed fetch-time rendering in the context. OPEN+FIND performs on-demand extraction but only from the current transient page. FTE performs on-demand extraction over a persistent, cache-addressable workspace.

The main causal comparison is FTE versus OPEN+FIND, but they differ in both persistence and cross-cache scope. The paper addresses this with a single-file grep ablation, while acknowledging that refused cross-cache calls add retry cost and make the ablation a lower bound rather than a clean estimate of persistence alone.

Experimental setup

BrowseComp measures deep multi-hop search; the paper uses a fixed random sample of 200 of 1,266 questions. WideSearch contains 200 broad table-filling tasks. Three backbones are tested: Qwen3.5-35B-A3B, Qwen3.5-122B-A10B, and DeepSeek-V4-Pro. Search uses Serper; page extraction uses crawl4ai; the visit-summary model is fixed to Qwen3.5-35B-A3B.

All runs allow up to 300 turns and retain the full interaction history without context management. Each cell is run three times, but only the best run is reported. DeepSeek-V4-Pro judges all outputs, including outputs produced by itself in the DeepSeek agent row.

Main results

FTE leads BrowseComp at every backbone: 44.5%, 52.5%, and 70.5%. The consistent ordering is FTE > OPEN+FIND > VISIT-SUMMARY > VISIT-SNIPPET > SNIPPET-ONLY. Relative to OPEN+FIND, gains are +2.5, +2.0, and +4.5 points; relative to VISIT-SUMMARY, +7.0, +4.5, and +6.5 points.

WideSearch is much closer. FTE Row-F1 is 34.3, 39.1, and 51.4, compared with VISIT-SUMMARY at 35.5, 38.8, and 51.5. FTE consistently beats the weaker raw visit-snippet and OPEN+FIND baselines. The results suggest deferred repeatable extraction matters more for a single difficult fact than for broad high-recall table filling, where a good one-shot summary can be competitive.

Behavioral analysis and ablations

FTE builds modest caches of roughly 5–11 documents on BrowseComp and 11–15 on WideSearch. Whole-cache grep is used on only 1–10.5% of questions, yet restricting grep to one file reduces BrowseComp accuracy from 44.5 to 39.5 and WideSearch Row-F1 from 34.3 to 29.2. Removing grep or read also reduces performance, with localization via grep more important on BrowseComp.

The standout behavior is revisiting. FTE returns to 12–20% of BrowseComp documents and 67–76% of WideSearch documents after leaving them, far above transient interfaces. This supports the mechanism story, although the paper does not provide a matched causal analysis connecting individual successful answers to a specific revisit event.

Conclusion and appendices

The authors conclude that an agent’s working memory should live in a durable external substrate rather than only in the context window or a transient browser session. Proposed extensions include cross-trajectory memory and fetch-time entity/structure indexes to complement lexical grep.

Appendix A substantially improves reproducibility by specifying sampling parameters, the shared system prompt, cache naming and provenance, output bounds, and tool schemas. Appendix B shows that agents mostly use short regex patterns, target single files, seed reads from grep line numbers, and rarely refetch cached URLs. The appendix also exposes draft-quality issues: unresolved section/appendix references remain.

Figure 2 — Document-interface architecture (page 2)

Visit-and-ReadSearch snippet → visit(URL, goal) → one fixed chunk/summary enters context.
Failure: selection and extraction are welded; omitted content is unrecoverable without another visit.
OPEN+FINDOpen one page → inspect bounded window/find matches → open another page.
Failure: extraction is deferred, but the prior page is released and query scope is current-page only.
Fetch-then-ExploreFetch selected pages → store full normalized text in per-question cache → grep/read later across retained files.
Benefit: selection is cheap in context tokens, extraction is repeatable, and evidence persists.

Interpretation. The architecture cleanly shows why FTE is not merely “more context”: page bodies stay off-context, while only bounded evidence snippets enter the trajectory. Operational limit. Network fetch latency, disk cost, security, and stale-content handling are not represented.

Workflow — FTE execution contract

INPUT: question q
1. SEARCH: obtain titles, URLs, and snippets.
2. SELECT: fetch promising URLs into a private per-question directory.
   - deterministic URL-derived filename
   - provenance header: URL, fetched timestamp, character count
   - return only path/size/status to the model
3. LOCATE: grep a regex across the whole cache by default, or a known file.
4. EXPAND: read a bounded line range around a hit.
5. REVISE: repeat grep/read as the hypothesis changes; no refetch required.
6. ANSWER: synthesize evidence from bounded observations.
7. CLEANUP: remove the temporary cache after the trajectory.

Evaluation and appraisal

9.5/10

Relevance

Rationale. Directly addresses long-horizon search-agent harness design, persistent workspaces, RAG-like evidence handling, and context discipline.

Evidence basis. The method maps closely to research workflows that keep source artifacts outside the chat transcript and retrieve evidence on demand.

Principal limiting factor. It is not a clinical or pharmacy study.

What would change it. A production evaluation in the user’s actual ChatGPT/local-agent workflow would raise confidence.

7.5/10

Novelty

Rationale. The mechanism is simple and partly precedented, but the controlled isolation of document-interface persistence is a useful contribution.

Evidence basis. The paper distinguishes visit-and-read, transient browsing, and a persistent cache while holding search, harness, and backbone fixed.

Principal limiting factor. Filesystem memory and state externalization already exist in coding and search agents.

What would change it. A broader comparison against modern long-context, indexed, and shell-based workspaces would clarify incremental novelty.

7.0/10

Method strength

Rationale. The study has strong internal controls and useful ablations, but the reporting strategy weakens statistical confidence.

Evidence basis. Three backbones, two complementary benchmarks, fixed search/harness, behavioral metrics, and extraction-tool ablations.

Principal limiting factor. BrowseComp uses only 200 items; each cell reports the best of three runs; no uncertainty intervals or paired tests are reported.

What would change it. Report all runs, paired significance tests, multiple samples/seeds, and independent replications.

6.5/10

Evidence strength

Rationale. The direction of effect is consistent, but several headline margins are small and could be unstable.

Evidence basis. FTE leads BrowseComp at every backbone and beats OPEN+FIND in all six benchmark/backbone cells.

Principal limiting factor. The BrowseComp edge over OPEN+FIND is only 2.0–4.5 points (4–9 of 200 questions), and WideSearch differences versus VISIT-SUMMARY are −1.2 to +0.3 Row-F1.

What would change it. Confidence intervals, run-level distributions, and full-benchmark evaluation would materially raise the score.

5.5/10

External validity

Rationale. The result is credible for this harness, but production generalization is largely untested.

Evidence basis. The paper varies three model backbones and uses depth- and breadth-oriented open-web benchmarks.

Principal limiting factor. One search API, one crawler, one ReAct harness, benchmark-only tasks, no live deployment, no trained policies, and no cost/latency evaluation.

What would change it. Replicate across search backends, proprietary/frontier models, changing web conditions, and real research tasks.

9.0/10

Implementation value

Rationale. The design is unusually buildable: the tool surface, cache format, output bounds, system prompt, and evaluation setup are specified.

Evidence basis. Appendix A gives deterministic filenames, provenance headers, tool schemas, line-numbered grep/read behavior, and bounded outputs; code is linked.

Principal limiting factor. Operational concerns such as prompt injection, malicious pages, cache quotas, source freshness, and citation binding are not evaluated.

What would change it. A hardened reference implementation with security, telemetry, and cost benchmarks would raise the score.

Strengths

  • Good isolation strategy: search, harness, system prompt, crawler, and backbone are held fixed while the document interface changes.
  • Complementary benchmarks: BrowseComp stresses deep fact recovery; WideSearch stresses broad extraction.
  • Mechanism-level analysis: revisit rate, cache size, extraction mix, call sequences, and ablations go beyond a single leaderboard table.
  • High reproducibility potential: exact tool behavior, output caps, cache format, sampling parameters, prompt, and code repository are provided.
  • Actionable design: the method can be implemented with ordinary filesystem tools rather than a specialized vector database or additional agent.

Limitations

  • Best-of-three reporting and no uncertainty: no mean, variance, confidence interval, or statistical test.
  • Limited BrowseComp sample: 200 of 1,266 items; the 2–4.5 point edge over OPEN+FIND equals only 4–9 additional correct answers.
  • Benchmark-only evidence: no real analyst, clinical, software, or enterprise research tasks.
  • Single harness and web stack: one ReAct implementation, Serper, and crawl4ai; live-web drift is not controlled by a fixed snapshot.
  • Judge dependence: an LLM judge scores all cells, and the DeepSeek agent is judged by the same model family/model.
  • Cost and reliability gaps: no wall-clock latency, token cost, API cost, cache I/O, failure rate, source-access failure, or web-security analysis.
  • Mechanism not fully separated: persistence and cache-wide querying are jointly changed; the attempted separation is imperfect.
  • No dedicated failure taxonomy: the paper explains aggregate behavior but not where FTE causes wrong answers, misses evidence, or overfits regex patterns.

Overall interpretation

Overall: 7.5/10 as evidence; 9/10 as a build idea. The paper is stronger as a systems-design and implementation reference than as definitive proof of effect size. Its most durable insight is not “grep beats browsing,” but that selected source bodies should remain externally addressable after the agent moves on.

Implementation and workflow takeaways

Build nowUse a per-task workspace with deterministic source filenames and a manifest containing URL, retrieval time, content hash/size, and status.
Keep off-contextStore full documents externally. Return only metadata during selection, then inject bounded evidence windows when needed.
Default to cache-wide searchAllow the agent to search all retained sources without first remembering which file contains the fact.
Use line-addressable evidenceReturn stable line numbers or chunk IDs so locate→expand is cheap and auditable.
Bound every observationCap matches, context lines, read ranges, and bytes to prevent context explosions.
Instrument revisitsTrack when the agent returns to a source, what new evidence it extracts, and whether the revisit changes the answer.

Direct relevance to a chat/web workflow

The paper closely resembles a manual workflow in which a living Markdown or HTML file holds the project state while each prompt performs one bounded operation. The external artifact is the persistent workspace; the chat transcript becomes the control loop rather than the only memory. This reduces context churn and makes earlier material reusable after the task changes direction.

Practical chat-interface analogue
1. Maintain a workspace manifest file for the task.
2. Add source files/URLs to the workspace without pasting full bodies into the conversation.
3. Record source ID, local filename, date, and reason selected.
4. Ask targeted extraction questions against the workspace.
5. Append evidence entries with source + stable location + interpretation.
6. Re-query prior sources when the hypothesis changes.
7. Keep the final synthesis separate from the evidence ledger.

Hardening required before production use

  • Canonical URL normalization, content hashing, duplicate detection, expiration/freshness policy, and quota limits.
  • HTML/PDF normalization tests and explicit handling of inaccessible, dynamic, paywalled, or malformed pages.
  • Prompt-injection and malicious-content defenses before cached page text is shown to the model.
  • Evidence-to-claim binding: final claims should point to source IDs and stable line/chunk ranges.
  • Telemetry for token usage, wall-clock time, search/fetch failures, cache growth, and answer changes after revisits.
  • Fallback retrieval beyond regex: entity indexes, semantic retrieval, structure-aware table/heading indexes, and OCR only when needed.

What not to overclaim

  • Do not infer that filesystem grep is universally better than vector search or long-context reading; those were not the main comparators.
  • Do not infer that FTE reduces total cost; only context exposure and search-call substitution are measured indirectly.
  • Do not infer that persistence alone caused the gains; cache-wide addressability is part of the mechanism.
  • Do not infer production safety, citation accuracy, or robustness from benchmark accuracy.

Bottom line

Best use: architecture reference for long-horizon research agents, local wrappers, custom tools, and structured chat workflows that need to revisit source material without repeatedly injecting entire documents into context.
Do not use for: estimating guaranteed accuracy gains, choosing a production system solely from leaderboard numbers, or making claims about safety/cost/latency that the paper did not measure.

Reading priority: Read first. Focus on Figure 2, Tables 2–5, Appendix A.2, and the reporting caveat in §4.1 that each cell is the best of three runs.

Confidence in appraisal: Moderate-high. The PDF provides enough methodological and numerical detail for a strong appraisal, but the absence of run-level uncertainty and the unresolved draft references prevent high confidence in the exact effect sizes.
